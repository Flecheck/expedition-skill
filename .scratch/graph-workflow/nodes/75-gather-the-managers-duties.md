# Gather the manager's accumulated duties into one enumerated list

Type: precondition
Status: resolved

## Question

**The manager is the only actor in this workflow with no contract.** `.claude/skills/` holds six worker contracts
and `expedition/graph-conventions.md`; nothing describes what the manager does. Its duties have accumulated across
the effort as consequences of other nodes' answers, and they sit **on those nodes** rather than anywhere a manager
could read them.

### The human's instruction, `verbatim`

> *"I think the priority should be writing the first version of the manager skill as now you don't have any way to
> know what to follow as the information is split everywhere."*

### Measured, so the size is not guessed

**20 node files name a duty of the manager's.** The fog paragraph that tracked them, now in `map-history.md`, ran to
**17,497 characters** before it was compressed to a pointer. The requirements were deliberately left on their
producing nodes under this effort's own rule that an item cites rather than restates — **which is right for the map
and is exactly what makes the skill unwritable without this node.**

## Why this is its own node, and the alternative that was rejected

**The obvious move is one implementation node that writes the skill.** It fails on [An acceptance condition is
self-contained text](33-condition-is-self-contained.md): a condition saying *"state the duties the graph has
accumulated"* points at material the blind checker will not be given, and a condition that **enumerates** them can
only be written by someone who has first gathered them. So the gathering happens either way; the only question is
whether it happens inside a condition the manager writes, or as work with its own output.

**It is put here for three reasons.** The manager writing it would spend the effort's scarcest resource — [Friction
from running this map by hand](24-self-hosted-friction.md) found the manager's context is what has failed every
session, and this session's own gathering would be ~20 node files. [A worker's handover carries no acceptance
condition for the node it mints](35-handover-mints-no-condition.md) **measured** that every condition written by a
spawning node's worker passes the self-containment rule while nine of thirty-one others fail. And the manager is the
one party that cannot check its own account of its duties, having formed those duties by doing them.

**Its type is `precondition` rather than `research`**: nothing here is decided and nothing outside this repository is
consulted. It is work that must happen before the skill can be specified.

## Acceptance condition

*Written by the manager, which minted this node, under [A worker's handover carries no acceptance condition for the
node it mints](35-handover-mints-no-condition.md)'s permission and marked as the manager's own.*

The work is `/home/mathieu/projects/graph-agent/.scratch/graph-workflow/`. Done means all of the following.

1. This node's `## Answer` holds **one enumerated list of every duty, rule and constraint the manager is under**,
   each item stating the duty in its own words and citing by markdown link the node that produced it. A duty that
   several nodes shaped carries several links.
2. The list is derived **by reading the node files rather than the map**. Every `resolved` node's `## Answer`
   and every `## Annotation:` section in it is read; the rest of a node file is read only where the answer points
   into it. The answer states how many nodes were read and how many produced a manager duty. Where a node was read
   and produced none, it is not listed.
   *Measured before this clause was written: there are 45 `resolved` nodes totalling 1,190,492 characters, of which
   the answers and annotations are 575,779. Reading whole files is not achievable in one session; reading answers
   and annotations is. A settled duty is stated in an answer, which is why the narrower target loses nothing.*
3. **The reading is ordered so that running short degrades gracefully.** `decisions.md` holds one capped line per
   resolved node; it is used to order the reading, most-likely-to-carry-a-duty first, and it is **not** used as a
   source for the list itself. If the work cannot be finished, the answer says which nodes were not reached rather
   than presenting a partial list as complete.
4. The list separates, under headings of the author's choosing, at least: what the manager **writes** and where;
   what it **may not** write or author; what travels in a **spawn**; what it does with a **handover**; what it does
   at a **gate**; what it does with a **flag**; how it **reports to the human**; and what it does when an agent
   **dies, stops or returns something it cannot file**.
5. Where two nodes' duties **conflict or overlap**, the answer says so and does not resolve it. Resolving one would
   be a decision, which this node's type does not permit.
6. The answer names every duty the manager is currently observing **that no node ever settled** — practice the
   manager adopted on its own authority — separately from the settled ones, so the human can see what has never been
   ruled on.
7. This node's `## Answer` ends with an **acceptance condition for the node that writes the skill**, written as
   self-contained text under node 33's rule: it demands only what the condition itself states, and a blind checker
   given that condition and the bar can establish every clause without being handed the graph.
8. No file outside `.scratch/graph-workflow/` is modified, and no shipped skill file is written by this node.
9. The bar.

## Answer

*The reading, stated so the count is not guessed.* **All 45 `resolved` nodes were read** — every `## Answer` and every `## Annotation:` section in each, 480,240 characters extracted from the 45 files and read in full. Nothing was left unreached, so clause 3's shortfall route did not fire. The reading was ordered from `decisions.md`, most-likely-to-carry-a-duty first; `decisions.md` was used for that ordering only and is not a source for any item below. **43 of the 45 produced at least one manager duty.** The two that produced none are [Destination of this effort](01-destination.md) and [How much of the lifecycle the workflow owns](03-lifecycle-scope.md) — 03 is the borderline call, since it fixes that decision and implementation nodes share one graph, which is context the manager's skill will state rather than a duty it discharges.

Three further sources were read as supporting context and are **not** sources for the list: `.claude/skills/expedition/graph-conventions.md` (which already holds many of these duties as shipped procedures), `map.md` at commit `6fb738b` via `git show`, and the `## Question` of the 28 `open` nodes — the last two only for §Q. `flags.md` was left unread.

### A. What the manager is

1. **The manager is one long-lived thread that owns the graph, spawns one worker per node, and is the only party the human ever talks to.** It is an ordinary session of the harness; a worker is a spawned agent, resumed in place rather than replaced. [Runtime host](02-runtime-host.md), [Naming](14-naming.md)
2. **The manager does not become a declared subagent type, and never relies on a capability to enforce a rule.** A hard rule in this workflow binds by being read; what a worker *can* do is a property of the harness, and a clause of that kind is false on any harness that cannot enforce it. [Whether the workflow ships explicit subagent definitions](69-explicit-subagent-definitions.md)
3. **The manager's context is the constraint that actually fails, and it is a capacity rather than a bill.** ~200k tokens per node measured, against an inherited sizing rule of 100k; the manager's window is billed at the cached rate while every worker pays its whole opening payload uncached. So *the fleet is where the money goes and the manager is where the accuracy goes*, and every design that spends manager context freely was priced against the wrong constraint. [Friction from running this map by hand](24-self-hosted-friction.md), [How an agent workflow and its skills reduce their own token cost](52-token-cost-of-a-workflow.md)
4. **Most of the context lives in the workers, not in the manager.** A manager that ends a node holding everything the node held has failed at its job even if the node resolved. [Friction from running this map by hand](24-self-hosted-friction.md)

### B. What the manager writes, and where

5. **The manager is the graph's only writer.** No worker writes any graph file, and no procedure in the conventions document is ever performed by a worker. [Subagent context contract](12-subagent-context-contract.md), [Graph file format](13-graph-file-format.md), [Cascade pass mechanics](15-cascade-pass-mechanics.md)
6. **It writes as a scribe: it pastes each part of a handover under its heading and never re-authors, shortens, re-orders, re-renders or improves it.** What the manager has of its own goes beside that text as its own marked note. Two grounds: a paraphrase silently becomes the permanent record, and re-authoring every resolution is the one cost that grows with the graph. [Subagent context contract](12-subagent-context-contract.md), [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md)
7. **The graph is written the moment the human speaks.** Their answer goes into `## Interview` or `## Review` at relay time; resuming a worker is a background send, so the manager issues the resume and the write in one turn. What this protects is that the answer reaches disk before the worker can return. [Subagent context contract](12-subagent-context-contract.md), [Human review of landed code](20-human-code-review.md), [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md)
8. **Every recorded answer carries `verbatim` or `paraphrase`, and the manager pastes the reply as the human wrote it, however terse.** *"ok for recommended"* is a complete answer. The option it points at is quoted in the same entry and attributed to whoever wrote it, usually the worker. Nothing is rendered, so nothing is `paraphrase` unless rendering was genuinely unavoidable — copying is the manager's cheapest act and yields `verbatim` every time, which is what stops the marker needing a judgement. Where a terse reply does not say which option it points at, the manager records the reply and asks which. [What is recorded when the human takes an option as offered](25-recording-an-option-taken.md), [Relay protocol](08-relay-protocol.md), [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md)
9. **The manager allocates node ids** — the next unused `NN`, sequential, stable, never reused. No locking is needed because it is the single writer. [Graph file format](13-graph-file-format.md), [Relay protocol](08-relay-protocol.md), [Revision semantics](06-revision-semantics.md)
10. **It creates a node file with its mandatory fields and its `## Question`**, fields in the header block only, and where several nodes are created at once it writes every file first and wires `Blocked by:` in a second pass. [Graph file format](13-graph-file-format.md), [Write the graph conventions document](21-conventions-document.md)
11. **On resolution it appends the `## Answer`, then sets the status, then appends one capped line to `decisions.md`** — one sentence, ~25 words, grouped by label where a vocabulary exists. The answer is written before the status changes, and the index line never restates the decision. [Graph file format](13-graph-file-format.md), [Write the graph conventions document](21-conventions-document.md)
12. **It maintains a region of `map.md` that no node owns**: the declared label vocabulary, the bar's commands once discovered for the repo, the review route once discovered, standing steering the human gives, and the two optional blocks — the effort's ground rules and a standing over sources by path and glob. This is the one growing region of the map that has not decayed. [Graph file format](13-graph-file-format.md), [Done-ness and termination](10-done-ness.md), [What the manager works on next](16-human-steering.md), [Subagent context contract](12-subagent-context-contract.md), [What keeps the shipped files consistent](29-shipped-file-consistency.md), [Friction from running this map by hand](24-self-hosted-friction.md)
13. **The map holds only each item's current statement and its links; the account moves verbatim to `map-history.md` first, and only then is `map.md` rewritten.** The map is rewritten as it changes rather than grown by appending, because every worker reads it whole, cold, once per node. Moved text moves byte-verbatim, struck text moves struck, and the account is written before the map changes so a run that dies leaves it banked. [What the token findings change](53-what-token-findings-change.md), [Restructure `map.md` to what every worker needs](59-restructure-the-map.md), [Say in the conventions document how the map and its history are written](64-conventions-say-how-the-map-is-written.md)
14. **No edit deletes.** Superseded text is struck or marked in place and new text is added around it; information leaves a file only when it is clearly wrong or the human asks for it gone. This binds the manager when it edits the map, where quiet deletion is most damaging and least visible. [Revision semantics](06-revision-semantics.md)
15. **Supersession bookkeeping is the manager's, step by step**: create the replacements carrying `Supersedes: NN`, mark the superseded text in place, add `Superseded by:` then set the status, repoint every inbound `Blocked by:` onto the replacement or replacements, and strike the old `decisions.md` line. The replacements exist before the old node is marked. These are the manager's procedural steps and never a cascade agent's writes. [Revision semantics](06-revision-semantics.md), [Graph file format](13-graph-file-format.md), [Cascade pass mechanics](15-cascade-pass-mechanics.md)
16. **When a later node changes what an earlier resolved node says, the manager files an annotation onto that node in the reporting worker's own words.** Measured: of twenty-eight propagations, eighteen landed on already-resolved nodes and fifteen of those came through the manager's own reading rather than through a worker's `INVALIDATIONS`. [Cascade pass mechanics](15-cascade-pass-mechanics.md)
17. **On a stop, the manager writes the salvage without reading it** — path-limited, with the node's paths marked intent-to-add first so a from-scratch diff is not silently empty — into the effort's own directory rather than the product tree. The pointer is inherited by whatever node succeeds the stopped one. [When an AFK worker cannot proceed](23-worker-cannot-proceed.md)
18. **For a node it minted itself, the manager writes the acceptance condition, records its own read-back on the node, and marks the condition as its own.** See §M. [Who writes the acceptance condition for an implementation node the manager mints itself](39-condition-for-a-manager-minted-node.md)

### C. What the manager may not write or author

19. **There is no path on which the manager answers anything.** Both *"you decide"* and a mid-interview reframe route to the worker, which holds the interview. The manager's temptation to shortcut either is the failure the relay exists to prevent. [Relay protocol](08-relay-protocol.md), [What the manager works on next](16-human-steering.md)
20. **It may never infer whole-node delegation from a per-question "you decide".** Silence about scope means per-question, because widening it on inference silently removes the human from a node. [Relay protocol](08-relay-protocol.md)
21. **It never renders a diff into the conversation**, and it assembles a chronology rather than summarising one: ordering pasted pieces is scribe work, rewriting them into a gloss is not. A chronology long enough to want shortening is a signal that the node was too coarse, not a formatting problem. [Human review of landed code](20-human-code-review.md)
22. **It never supplies what an acceptance condition omits on the way to the checker.** It hands a pointing condition over as written; where what is missing is what the check turns on, that goes to the human. Supplying it would make the manager the author of the standard the work is judged against. [An acceptance condition is self-contained text](33-condition-is-self-contained.md), [The clause that says no resolved node changes cannot be self-contained](36-resolved-node-clause-cannot-be-self-contained.md)
23. **It never authors an acceptance condition for a node a *worker* minted, and never authors a worker's flag text** — neither the node's `## Flags` prose nor the `flags.md` line. Both were workarounds for a missing handover part and both are now explicitly wrong. [A worker's handover carries no acceptance condition for the node it mints](35-handover-mints-no-condition.md)
24. **It never rewrites an acceptance condition.** A worker may not either; the human may, mid-attempt, in place with the old text struck — the third revision case, permitted because the condition's author is the spawning node and the human outranks it. [When an AFK worker cannot proceed](23-worker-cannot-proceed.md), [Node type taxonomy](07-node-type-taxonomy.md)
25. **A spawn may not depart from the contract it names on the manager's authority.** Where a clause blocks the node in front of it, the manager **raises**; the human's answer produces two outputs, always both — a licence for that one attempt, recorded as a flag on the node, and a node for the permanent fix. A licence is not an amendment: nothing on disk changes. Amending a contract is an implementation node against that skill file, never something the manager does mid-flight. [Whether a spawn may override a shipped worker contract](28-spawn-overriding-a-contract.md), [Off-contract subagent output](17-off-contract-output.md)
26. **Nothing the manager sends a worker may widen what that worker writes.** The write rules are what keep the manager the graph's only writer, and this floor is written over anything the manager sends — not only over the first message, because three of four observed departures arrived on a resume. [Whether a spawn may override a shipped worker contract](28-spawn-overriding-a-contract.md)
27. **A manager note may name which of a worker's questions it believes sharpest, and may not say what it thinks the answer is.** The boundary is the sharpest / the answer line. [What the manager works on next](16-human-steering.md)
28. **Only the human closes an effort. The manager never does.** [Done-ness and termination](10-done-ness.md)
29. **The manager cannot arbitrate between a worker and its checker.** It is a scribe and it answers nothing, so that disagreement has exactly one referee — the human. Today the implementation contract closes the flag route by name and none of the three raise triggers fits, so a worker convinced a finding is false must either edit code that is not broken or depart from its contract. **Unsettled**: [What an implementer does with a checker finding it believes is false](34-implementer-disputes-a-finding.md).

### D. What travels in a spawn

30. **The spawn is a dispatch, not a briefing**: the node's name and path, the statement that the worker is not the manager and has no channel to the human, the contract to invoke, three pointers, the per-type additions, and optional manager notes. [Subagent context contract](12-subagent-context-contract.md)
31. **The contract travels as a skill invocation, not as prompt text** — the human's call. The spawn names the contract's path and states that the file on disk wins, because the harness serves the skill body it loaded and a mid-session edit does not reach an already-running session's registry. [Subagent context contract](12-subagent-context-contract.md), [Write the worker contract skills](22-worker-contract-skills.md), [Re-review the shipped files against `/writing-for-agents`](54-review-against-writing-for-agents.md)
32. **The pointer set is exactly three**: the node's own file, `map.md`, and `decisions.md` scoped by label. Scoping is a filter instruction, not an extract — the pointer stays a pointer. `flags.md` stays out of every set. The glossary is not a pointer at all: it ships inside the contract. [Subagent context contract](12-subagent-context-contract.md), [Graph file format](13-graph-file-format.md)
33. **A manager note is capped at context the manager already holds.** It does not read code or run research to produce one. Without the cap the manager duplicates the worker's work and becomes a second implementer instead of a second pair of eyes. [Relay protocol](08-relay-protocol.md)
34. **Two things in a spawn are not manager notes and are not governed by that cap**, because neither is the manager's own: **a carried direction of the human's**, marked as their words rather than the manager's and recorded as a flag on the node; and **a licence granted by a manager raise**. On an effort whose repository does not own the thing being fixed, the human's carried instruction is the *only* route past friction that blocks. [Subagent context contract](12-subagent-context-contract.md), [Whether a spawn may override a shipped worker contract](28-spawn-overriding-a-contract.md), [Workflow self-improvement during use](19-workflow-self-improvement.md)
35. **Per-type additions**: `research` gets the sources and their standing and that it may read outside the working directory; `prototype` gets `prototypes/NN-<name>/` and that the artifact is discarded; `implementation` gets its `## Acceptance condition`, the bar via the map, and the paths the spawning node expects it to touch — **orientation, not permission**, so a worker that writes outside the list is not in violation and simply reports what it touched; `precondition` gets what must be true when it is done and which resulting facts later nodes depend on; `grilling` gets nothing extra. [Subagent context contract](12-subagent-context-contract.md)
36. **The checker's spawn is different in kind, and the manager is the party that composes it.** Five givens: the acceptance condition as **extracted text**, the bar, the paths that changed in the working tree holding them, the diff, and the effort's ground rules copied as text with the duty *"Follow them."* attached. Nothing else. It is the one worker whose payload cannot be a pointer, because pointing it at the node file would unblind it. Where the effort declares no ground rules, that given is absent. [Subagent context contract](12-subagent-context-contract.md), [The checker's spawn carries the effort's ground rules](42-checker-spawn-carries-ground-rules.md), [Human review of landed code](20-human-code-review.md), [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)
37. **The boundary on the ground-rules route**: only a standing constraint on the effort, true of any node's work, may travel it. An account of what happened — on this work or anywhere in the record — is never a ground rule and never travels by that route, that being exactly what the checker is kept blind to. [The checker's spawn carries the effort's ground rules](42-checker-spawn-carries-ground-rules.md), [What keeps the shipped files consistent](29-shipped-file-consistency.md)
38. **The manager starts the checker, not the implementer.** Whoever spawns it chooses what it sees, and the implementer has an interest in passing, so an implementer extracting its own condition can extract it favourably. Extraction is copying, which is the scribe's work and costs the manager nothing to keep. [Human review of landed code](20-human-code-review.md)
39. **The manager copies the ground-rules block as text and adds nothing of its own.** Where a check needs a constraint the block does not hold, that is a raise rather than the manager's judgement. [What keeps the shipped files consistent](29-shipped-file-consistency.md)
40. **A worker's spawn points it at the effort's own glossary where it has one**, and the shipped set's own documents must be reachable — `.claude/skills/expedition/` holding no `SKILL.md` is why nothing points at `graph-conventions.md` today. [What keeps the shipped files consistent](29-shipped-file-consistency.md)
41. **Keep spawn prompts focused**: everything in the spawn adds to the worker's context from the start, and a worker pays its entire opening payload uncached at full rate. A worker paused across a human answer is liable to come back cold, subagents using the five-minute TTL. [How an agent workflow and its skills reduce their own token cost](52-token-cost-of-a-workflow.md)
42. **A worker that must *invoke* rather than read a plugin skill has to be spawned from a session started after that plugin changed on disk**, the skill registry being loaded per process. [Re-review the shipped files against `/writing-for-agents`](54-review-against-writing-for-agents.md)

### E. What the manager does with a handover

43. **A worker returns exactly one of three things** — question, handover, or park — and the checker returns `PASS`, `FAIL`, or a raise that issues no verdict at all, with `QUESTIONS:` and `NOT COVERED:` riding alongside either outcome. A raise reuses the question shape and is not a fourth variant. [Subagent context contract](12-subagent-context-contract.md), [When an AFK worker cannot proceed](23-worker-cannot-proceed.md), [What the checker contract owes to having been run](31-checker-contract-owes.md)
44. **The test is fileability, never conformance.** A handover is on-contract when the manager can paste it under the node's headings — everything required present plus something the contract does not name, or a route the contract does not offer taken in place of one it does, are both filed. Only a missing required part, or a shape with no heading to sit under, is unfileable. Refusing a departure would have cost the four most valuable things a run produced. [Off-contract subagent output](17-off-contract-output.md)
45. **What a handover departs by becomes a flag beside it, filed by the manager against the node** — at the gate where the node has one, and as the manager closes the node where it does not. [Off-contract subagent output](17-off-contract-output.md)
46. **Before it files, the manager holds the handover's `ANSWER` against the `## Interview` it wrote itself**, and anything resting on words the human did not say is filed as a flag beside it rather than refused. This is the one join where the checking party already holds both sides, so nothing is re-read and nothing is re-derived. [Off-contract subagent output](17-off-contract-output.md), [What is recorded when the human takes an option as offered](25-recording-an-option-taken.md)
47. **A worker's `NEW NODES` and `INVALIDATIONS` are reported by the worker and by nothing else**, and the manager files them. Nothing today tells a worker to *go and look*, and nothing checks either part — **unsettled**: [Nothing tells a worker to hold its work against the record](37-invalidations-is-not-a-check.md). The channel's wording is due to widen from *contradicts* to *changes what it says* at [Widen the invalidation channel](43-widen-the-invalidation-channel.md), which is open.
48. **An implementation worker's handover carries a sixth part, the gate payload**, and the path list is *reported* rather than inferred from `git status`. [Subagent context contract](12-subagent-context-contract.md), [Git and code-landing policy](11-git-and-code-landing.md), [Write the worker contract skills](22-worker-contract-skills.md)
49. **A worker's report of which part of a method skill it left unrun, and why, is filed by the manager under the node's `## Answer`** as ordinary scribe work; it needs no flag, the rule being written down. [Reconcile a method skill's instructions with the contract's hard rules](48-method-skill-conflicts-hard-rules.md)
50. **`none` written out in full is load-bearing**: it is how the manager tells *looked and found nothing* from *did not look*, and it is the cheapest instrument in the design. [Subagent context contract](12-subagent-context-contract.md)

### F. What the manager does at a gate

51. **The manager refuses to raise the gate until the checker passes**, so the human never sees a node whose checker findings are still open. **One exception, stated rather than hidden**: a checker that will not pass must still reach the human, because the gate is the only place an implementation node becomes visible to them — the chronology carries *"it failed three times, here is why"* and the gate is raised on a failing tree with that stated in the first line. [Human review of landed code](20-human-code-review.md)
52. **The manager assembles the payload from other people's text and writes only one part of it itself**: the checker's chronology laid end to end oldest first; the flags the node holds; the node, the paths actually touched, and the proposed commit message with its `Node: <effort>/<NN>` trailer; and a pointer to the tree. **No rendered diff, and no acceptance condition** — a human checking the condition themselves is doing the checker's work. [Human review of landed code](20-human-code-review.md), [Git and code-landing policy](11-git-and-code-landing.md), [Naming](14-naming.md)
53. **A flag reaches the human as what was done, why, and the context it needs to be answered — and answering it never requires opening a file.** Neither of a flag's two existing forms is a payload, so the manager writes a third form for the gate. The human's words: *"Idealy I don't have to go into the files to find out what happened and how to respond."* [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md), [Human review of landed code](20-human-code-review.md)
54. **Three outcomes, and the manager routes on which it received**: *approve* → commit → the node resolves; *correct* → the worker fixes and the gate is re-raised, uncapped; *reject* → the graph edit is made **first**, then the tree is cleaned. [Human review of landed code](20-human-code-review.md)
55. **Reject is narrow and is a discovery, not a verdict on quality**: implementing the node taught the graph that this code should not exist. *Try again, differently* is a correction. **The enumeration of where a rejected node goes is the manager's**: past the destination → `out-of-scope`; the node asked the wrong question → `superseded` by a replacement; something upstream is wrong → `open` with a new `Blocked by:` edge. [Human review of landed code](20-human-code-review.md)
56. **On a reject the diff is discarded by default, with one line offering to keep it** — *"discarding `<paths>` — say so now if you want the diff kept."* Under worktrees keeping costs nothing: the work is committed onto the unmerged branch and the directory removed. [Human review of landed code](20-human-code-review.md), [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)
57. **The bar is re-checked every correction round. The acceptance condition is re-checked only when the worker reports that its correction touched something a condition names** — the trigger sits on the worker because it is the party that knows. [Human review of landed code](20-human-code-review.md)
58. **`## Review` holds three things and nothing beyond them**: the checker's chronology one entry per run, each naming `PASS`, or `FAIL` and which of the two it failed, or that it raised instead of judging; each correction round numbered with the human's words verbatim and what the worker changed; and the gate's outcome named as one of the three, with a reject also recording what popped up and which route was taken. [Human review of landed code](20-human-code-review.md), [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md)
59. **A part the checker did not cover is recorded on that run's own entry, under a line-anchored `NOT COVERED:` label, one item per part, each quoting the part as the checker wrote it.** The outcome on that entry then covers the rest of the condition and no more. [Record a checker's not-covered part on `## Review`](38-recording-a-not-covered-part.md)
60. **Every such item opens with its state and only two openings exist** — `OWED` or `ESTABLISHED BY <who> · <what they read or ran>` — and establishing rewrites that opening and nothing else. The open state is written, never inferred from an absence. Mechanical check 9 reads that marker and nothing else: no `resolved` node may still carry an item opening `OWED`. [Nothing checks that a part a checker left uncovered was ever established](45-nothing-checks-an-uncovered-part.md), [Record a checker's not-covered part on `## Review`](38-recording-a-not-covered-part.md)
61. **Establishing an uncovered part is usually the manager's**, because it holds the handover the checker does not; it may instead be the human at the gate or a later run of the check. **It happens by the gate at the latest**, the node resolving there with nothing after it to establish anything. [Record a checker's not-covered part on `## Review`](38-recording-a-not-covered-part.md)
62. **Where the human amends a condition while a check is live, the manager says so to the checker**; the amended text is then the whole of it, and a part established against wording that has since moved is established again. [What the checker contract owes to having been run](31-checker-contract-owes.md)
63. **An implementation node that changes a file other nodes of the same effort are written against names at its gate which files it moved and which are left in the older form, and the manager carries that statement into every later spawn and re-check.** [Workflow self-improvement during use](19-workflow-self-improvement.md)

### G. What the manager does with a flag

64. **A flag's two entries are the worker's text; the manager adds bookkeeping and nothing else** — the flag's id `NN.k`, the link to the node, and its state. [A worker's handover carries no acceptance condition for the node it mints](35-handover-mints-no-condition.md), [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md)
65. **Raising a flag is two writes in order**: the node's `## Flags` entry with its id and marker, then one unchecked line in `flags.md` carrying the same id and linking the node. Both belong to the act of raising, never to a tidy-up — a `## Flags` section assembled once does not stay assembled. [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md), [Write the graph conventions document](21-conventions-document.md)
66. **Settling a flag is two writes too**: `- [x]` in `flags.md` and `settled` on the node. **Where they disagree `flags.md` wins, because the sweep and the closing report are built from it.** [Whether flags.md survives the settle-at-close practice](27-does-flags-file-survive.md), [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md)
67. **Settling at the human moment that ends a node is the norm** — a grilling node's last answer, an implementation node's gate — while the work is still there and judging a flag is cheap. The closing report is the exception path: it carries only the flags that never had a human moment. [Whether flags.md survives the settle-at-close practice](27-does-flags-file-survive.md), [Human review of landed code](20-human-code-review.md), [Done-ness and termination](10-done-ness.md)
68. **`flags.md` is not a queue; it is the graph's capped index of every judgement an agent made on its own**, one report-shaped sentence per flag written at raise time by whoever holds the context and never reconstructed later. The manager never reconstructs it at report time. [Whether flags.md survives the settle-at-close practice](27-does-flags-file-survive.md)
69. **`CONDITION-WRONG` is the manager's flag to file, and only where a worker raised its condition as wrong and the human answered *carry on, ship it anyway*.** The worker's own markers are `ASSUMPTION` and `DELEGATED`. [When an AFK worker cannot proceed](23-worker-cannot-proceed.md), [Write the worker contract skills](22-worker-contract-skills.md), [Carry the recorded deltas into the shipped skill files](26-carry-deltas-into-shipped-files.md)
70. **A `FRICTION` flag is never settled as fixed on the effort that raised it.** Two dispositions and no third: *refused*, settled in place with the human's reason recorded; or *outstanding*, meaning carried and re-surfaced at that effort's close. No agent can tick the line, because no agent crosses a repository boundary. Nothing on such an effort may be made to wait on the skill being fixed, because that effort could never close. [Workflow self-improvement during use](19-workflow-self-improvement.md)
71. **Promoting is how banked work re-enters**: a flag the human names becomes a node, a parked node returns to the frontier with its banked answers intact. A `FRICTION` flag's node is minted in the repository holding the skill files, in a session there, and never on the graph that raised it — it is the human's act, not the foreign manager's. [Done-ness and termination](10-done-ness.md), [Naming](14-naming.md), [Workflow self-improvement during use](19-workflow-self-improvement.md), [What the manager works on next](16-human-steering.md)
72. **Nothing checks a flag before the human sees it, and the direction to change that is already the human's.** The design would give the manager two more re-authorings — a stripped claim for a checker and an expanded payload for the human — which are opposites and both land in the manager's hands. **Unsettled**: [Whether a flag is checked before the human settles it](30-checking-a-flag-before-the-human.md).

### H. How the manager reports to the human

73. **Exactly one question is in front of the human at a time, and nothing ever replaces a live question.** Everything else waits in a pending queue. The cost is bounded to one answer's latency, and the human holds the release valve — parking the live question moves the queue on immediately. [What the manager works on next](16-human-steering.md)
74. **The queue has two tiers, and tier 1 is closed at exactly three members**: a gate, a worker's blocking raise, and the manager's own raise. Tier 2 is a relayed interview question. Within a tier, arrival. **The closure is not an extensible rule** — adding a fourth member is a decision, not an inference. [What the manager works on next](16-human-steering.md)
75. **Three things are not claimants at all**: flag settlement, which rides the human moment that already ends its node; a death notification, which awaits no answer; and the closing report, which ends the effort rather than taking a turn in it. [What the manager works on next](16-human-steering.md)
76. **Every relayed question names in one line whatever else is waiting, by node name and kind only** — never restating the other question or its options. It is a `MANAGER NOTES` line drawn from context the manager already holds, and keeping it to a name and a kind is what keeps a terse reply attributable to exactly one thing. [What the manager works on next](16-human-steering.md)
77. **The relay payload upward is fixed**: `NODE`, `ABOUT`, `SO FAR`, `ASK` (the worker's question verbatim), `RECOMMENDED`, `ALTERNATIVES`, and optional `MANAGER NOTES`. `ABOUT` and `SO FAR` exist because the human has read none of what the worker read; a frame-less question spends the scarce resource on orientation instead of judgement. [Relay protocol](08-relay-protocol.md)
78. **Downward it is `HUMAN ANSWER` verbatim, `DIVERGENCE` where the answer contradicts the worker's recommendation, and `MANAGER NOTES` marked as the manager's and never blended into the human's answer.** `DIVERGENCE` is load-bearing: without it a worker resolves as though it had won its point. [Relay protocol](08-relay-protocol.md)
79. **The manager picks the next node and reports the pick; it never asks.** A *"which node next?"* confirmation would occupy the single channel that exists for real work, and a pick is cheap to undo. The human's override is one line. [What the manager works on next](16-human-steering.md)
80. **Three states are invisible in the graph files and the manager must be able to report them**, a node reading `claimed` like any other: which node awaits approval at a gate, whether a worker is blocked on a raise, and what is banked and waiting. The first two the manager volunteers; the third it answers on request. [What the manager works on next](16-human-steering.md), [Git and code-landing policy](11-git-and-code-landing.md), [When an AFK worker cannot proceed](23-worker-cannot-proceed.md)
81. **The manager names in its ordinary narration at each resolution what the cascade pass minted, or that it found nothing.** That is what stops a pass which supersedes eleven nodes from being a surprise at the next human read. [Cascade pass mechanics](15-cascade-pass-mechanics.md)
82. **The pick report also names a manager-written acceptance condition as the manager's own and, in a line or two, what it demands — and the work does not wait for a reply.** [Who writes the acceptance condition for an implementation node the manager mints itself](39-condition-for-a-manager-minted-node.md)
83. **The manager reports a standing steering instruction back in every pick it constrains**, so an emphasis nobody remembers setting cannot be silently forgotten. [What the manager works on next](16-human-steering.md)
84. **Nothing lists what the report contains.** At least four duties have accumulated on it from three nodes and no file collates them — the same failure shape [What keeps the shipped files consistent](29-shipped-file-consistency.md) exists because of. **Unsettled**: [What the manager reports to the human, in one place](46-what-the-manager-reports.md).

### I. What the manager does when an agent dies, stops, or returns something it cannot file

85. **Death is detected lazily and only by a failed resume.** The manager can neither read a running worker's transcript nor inspect a dead one. A key that fails to resume means gone, and the manager marks that attempt dead rather than retrying it. **This is why the manager attempts a resume first: the attempt *is* the detector.** [Relay protocol](08-relay-protocol.md)
86. **Recovery is automatic and AFK.** The node keeps its number, its file and its claim — **the claim belongs to the node, not the agent instance**, and is never released by a crash. A fresh worker is spawned with the node plus the full replayed transcript and an instruction that already-answered questions are settled facts, never to be re-asked. Its new routing key is appended as the next attempt. [Relay protocol](08-relay-protocol.md), [Node type taxonomy](07-node-type-taxonomy.md)
87. **The human is told once, by node name**: that the agent for that node died, that their answer is recorded and being replayed, and that they will never see the same question twice. It awaits no answer. [Relay protocol](08-relay-protocol.md), [What the manager works on next](16-human-steering.md)
88. **Capped at two respawns, and at most three `## Interview` attempt blocks.** Replay re-inflates exactly the context that killed the previous attempt, so a third failure is evidence the node is too coarse and escalates to the human as a graph-shape decision; the node holds work by then, so its replacements arrive by ordinary supersession. [Relay protocol](08-relay-protocol.md), [Write the graph conventions document](21-conventions-document.md)
89. **Death and replay reach implementation nodes too**, with `## Review` as the log instead of `## Interview` and the working tree as a second piece of recoverable state no interview ever had. [Relay protocol](08-relay-protocol.md), [Git and code-landing policy](11-git-and-code-landing.md), [Human review of landed code](20-human-code-review.md)
90. **A worker the human *stopped* cannot be resumed at all** — the harness refuses and treats its work as cancelled — so re-prompting can simply be unavailable and what remains is a fresh attempt. A mis-click costs a whole check. [Off-contract subagent output](17-off-contract-output.md), [Write the worker contract skills](22-worker-contract-skills.md)
91. **An unfileable return is re-prompted exactly once, naming which part is missing.** A second unfileable return is neither re-prompted again nor respawned: the manager files what it can, leaves the node `open` holding what is already on it, and tells the human once by node name. The relay's cap of two does not transfer, because nothing is replayed here. **Nothing rejected is written onto the node.** [Off-contract subagent output](17-off-contract-output.md)
92. **Park is three steps in order**: instruct the worker to store its progress and stop; append the returned progress to `## Interview` under the current attempt, with every question already answered and the human's words verbatim rather than summarised; then set `Status: open`. Progress before status. The HITL slot frees the instant the human says it. [Relay protocol](08-relay-protocol.md), [Write the graph conventions document](21-conventions-document.md)
93. **On a `stop` answer to a raise the manager kills the worker, saves the salvage, cleans the tree, frees the slot and hands the node back as ordinary graph work.** Every stop route leaves the node either not `open` at all or `open` with a new `Blocked by:` edge, so a stopped node is never mistaken for a parked one — and that is a **constraint on any future stop route**, not a coincidence of these three. [When an AFK worker cannot proceed](23-worker-cannot-proceed.md)
94. **Under worktrees the death signature is a live worktree with no `claimed` node**, replacing the old heuristic that read a dirty tree as a dead worker. [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)

### J. What the manager works on next

95. **The frontier is read as two streams — design and delivery — and free capacity is filled by alternating between them**, skipping a stream with nothing to offer, with a very-high-level node pre-empting either. Written over capacity `n` rather than named slots, because the count is the human's to set. Depth-first falls out for free. A `precondition` node joins whichever stream it serves. [What the manager works on next](16-human-steering.md)
96. **Fan-out is refused as the metric.** Unblocking many is a symptom of generality, not the thing to rank on; measured, fan-out was zero for every node on this frontier. The policy is judgement over the node's text at pick time, and the cost is that it does not keep open the cheap-manager door a computable ranking would have. [What the manager works on next](16-human-steering.md)
97. **Interview slots count nodes in flight; the queue rule counts questions in front of the human, which is one.** Concurrency buys node throughput, not answer throughput, and slots past the human's answering rate buy half-finished interviews. The default stays near two. [What the manager works on next](16-human-steering.md), [Concurrency model](04-concurrency-model.md)
98. **The readiness floor**: an implementation is startable when its acceptance condition can be written in full, with nothing deferred to an open question. **Discharging the floor by deciding the open question inside the condition does not pass** — that is a manager decision reaching the graph, which is a raise or a flag, never a condition. The honest move is to state the property precisely and leave the form to the worker. [What the manager works on next](16-human-steering.md)
99. **A blocking raise pre-empts.** The manager stops feeding the human's queue with grilling questions and asks. Pre-emption acts on the queue and never on the live question. [When an AFK worker cannot proceed](23-worker-cannot-proceed.md), [What the manager works on next](16-human-steering.md)
100. **Code revisions jump the exclusive code slot ahead of new code work; decision revisions queue normally.** A superseded implementation means the repo holds code known to be wrong right now. [Revision semantics](06-revision-semantics.md)
101. **A `Labels:` scope filters the frontier before any stream rule is applied, and can never be a priority signal.** An ordering across areas arrives as standing steering, not from the label field. [Graph file format](13-graph-file-format.md), [What the manager works on next](16-human-steering.md)
102. **Steering has two forms.** A named node is one pick, expires when used, and parks nothing. A scope or an emphasis is standing, and the manager writes it into `map.md`'s `## Notes` — the only durable home, because steering held only in the manager's context dies with the session. [What the manager works on next](16-human-steering.md)
103. **The manager schedules a coverage checklist on a dogfood run**: the migration, all five node types at least once, the relay, at least one human redirect used because the human wanted it, concurrency, an implementation node with a spawner-written condition checked independently, and code actually landing. Four more must not be faked — supersession of a node holding work, a cascade pass, a death-and-respawn recovery, and termination — and *"not yet observed"* is a legitimate result. [Dogfood target](09-dogfood-target.md)

### K. The code slot, the worktree, and landing code

104. **The code slot is a count in the map's Notes, and the count is one.** *Exclusive* stopped being a property of the design and became a number; raising it later changes a number and no part of the lifecycle. [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md), [Concurrency model](04-concurrency-model.md)
105. **The manager creates a git worktree per implementation node before it spawns the worker** — `git worktree add -b expedition/<effort>/<NN> <path> HEAD` — placed **outside** the repository's working tree, so it never shows up as untracked in the human's `git status`. The branch carries the node's id and is deleted with the worktree. It is never pushed. [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)
106. **The live worktrees are the occupied slots.** One per claimed implementation node; the human's own tree no longer participates in the signal at all. [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)
107. **On approval the manager commits, rebases onto the branch the manager thread is on, re-runs the bar, fast-forward merges, and removes the worktree.** The condition is a statement about this node's work so it is checked in the worktree; the bar is a property of a tree so it must hold of the tree that lands. **Absorbing the human's own periodic graph commits is the rebase's real job**, which is why the rebase is needed even at a count of one. A post-rebase bar failure takes a correction round. [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)
108. **A rebase conflict is nobody's to resolve silently**: the manager runs `git rebase --abort`, which restores the worktree exactly, and the node takes a correction round with the worker respawned on the new base. The manager does not author code. [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)
109. **One path-limited commit per implementation node, containing only that node's code, only after the human has approved it.** `git add -- <files>` then `git commit -- <paths>`; never `git add -A`, never `git commit -a`. A path-limited commit never needs to know what a repo ignores and leaves the human's own index untouched. [Git and code-landing policy](11-git-and-code-landing.md)
110. **If the product tree holds uncommitted code the node did not write, the manager stops and says so** rather than committing someone else's work under a node's name. [Git and code-landing policy](11-git-and-code-landing.md)
111. **The commit message carries `Node: <effort>/<NN>` as a trailer in the body.** The effort name is required because `NN` restarts at `01` per effort and the cascade *acts* on that query. The manager proposes the message and the human sees it before the commit. [Git and code-landing policy](11-git-and-code-landing.md), [Naming](14-naming.md)
112. **The workflow never pushes, and never rewrites history except for the per-node rebase.** Push is always the human's act. The graph's own files are not committed per node; the human commits them periodically, which is safe only because node files are append-only. [Git and code-landing policy](11-git-and-code-landing.md), [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md)
113. **Prototype artifacts land under the effort's own directory, tracked but outside the product tree**, so they never contend for the code slot and never pass the gate. Escape hatch, stated rather than built for: a prototype that can only exist inside the product tree takes the slot and the gate like an implementation node. [Git and code-landing policy](11-git-and-code-landing.md), [Node type taxonomy](07-node-type-taxonomy.md)
114. **Nothing confines a worker to its worktree except the instruction to stay there.** It is isolation of the human's tree from accidents, not a sandbox. [Run an implementation node's work in a worktree](68-implementation-in-a-worktree.md), [Whether the workflow ships explicit subagent definitions](69-explicit-subagent-definitions.md)
115. **The async switch is one step and it has a trigger**: the manager commits *before* the gate instead of after, and the trigger is the code slot idling on human attention — which now has two claimants rather than one, so it arrives sooner. After a commit, reject becomes a forward revert. [Git and code-landing policy](11-git-and-code-landing.md), [When an AFK worker cannot proceed](23-worker-cannot-proceed.md)
116. **An effort's graph lives in the repo the effort changes, and each repo's effort follows the same policy.** Nothing cross-repo is coordinated. [Git and code-landing policy](11-git-and-code-landing.md)

### L. Revision, the cascade, and the sweep

117. **One test decides which mechanism applies: is there work in this node to preserve?** Not started → update in place. Holds an answer or landed code → supersede, with replacement nodes of any shape and a mandatory forward pointer. The test governs revision arriving from *outside* the node: a node under its own checker's scrutiny is neither. [Revision semantics](06-revision-semantics.md), [Node type taxonomy](07-node-type-taxonomy.md)
118. **A `Blocked by:` pointing at a superseded or out-of-scope node is an error, not a satisfied edge**, and ruling something out of scope does not close an effort by itself. [Revision semantics](06-revision-semantics.md), [Done-ness and termination](10-done-ness.md), [Graph file format](13-graph-file-format.md)
119. **A session about to supersede a node that is itself a replacement escalates to the human as a decision instead of revising again.** There is no depth counter and no budget; the chain makes friction visible. [Revision semantics](06-revision-semantics.md)
120. **The manager spawns a triage agent at every resolution.** Its whole input is the answer that just resolved plus the landed-code inventory — one line per node that ever landed code, from `git log --grep '^Node: <effort>/'`. It reads no product code, and **the empty result is the ordinary one**. [Cascade pass mechanics](15-cascade-pass-mechanics.md)
121. **Each survivor gets its own agent**, handed that node's answer, its commits from the anchored `git log --grep '^Node: <effort>/<NN>$'`, and its files. The anchors are load-bearing: unanchored, `Node: <effort>/4` matches 4, 40–49 and 400 upward. [Cascade pass mechanics](15-cascade-pass-mechanics.md), [Naming](14-naming.md)
122. **No agent in the pass writes a graph file, and the pass never edits product code.** Its only output is a node to be minted: `implementation` where the fix is determined, `grilling` or `research` where it is not. Its condition is written by the per-candidate agent, so such a node is **not** manager-minted. [Cascade pass mechanics](15-cascade-pass-mechanics.md), [A worker's handover carries no acceptance condition for the node it mints](35-handover-mints-no-condition.md)
123. **The per-candidate agent does not run while the code slot is occupied; triage reads no product code and never waits.** Waiting costs nothing, the pass being AFK and its output a queued node. [Cascade pass mechanics](15-cascade-pass-mechanics.md)
124. **Open-node targets stay manual**: the manager keeps reading its own answers and appending the marked note by hand. Sharpening an unstarted node's acceptance condition is an open-node edit and stays with the manager. [Cascade pass mechanics](15-cascade-pass-mechanics.md), [Node type taxonomy](07-node-type-taxonomy.md)
125. **The pass raises no flag of its own**, and where it cannot judge it says so in its return and mints nothing. [Cascade pass mechanics](15-cascade-pass-mechanics.md)
126. **The sweep is the same machinery with the bound taken off**: triage with every resolved answer as its input, fanning out identically, plus a single read of `flags.md`. It runs only on an empty frontier. [Done-ness and termination](10-done-ness.md), [Cascade pass mechanics](15-cascade-pass-mechanics.md)
127. **No audit agent sits over the cascade.** The backstops are the bar, the mechanical checks, and the human reading the changes; the named residual risk is a semantic miss in code that builds cleanly in a file the human did not read. [Done-ness and termination](10-done-ness.md)
128. **The cascade pass has no worker contract yet.** [Write the cascade pass's worker contract](44-cascade-worker-contract.md) is open.

### M. Acceptance conditions

129. **An implementation node may not be claimed until it carries an acceptance condition** — mechanical check 7. [Node type taxonomy](07-node-type-taxonomy.md), [Write the graph conventions document](21-conventions-document.md)
130. **A condition is self-contained text.** A path may say *where*, because the checker has the repo; the demand itself may never sit outside the text. Material genuinely held elsewhere is copied in. **The bar is the one exemption**, and only because it reaches the checker by its own route. [An acceptance condition is self-contained text](33-condition-is-self-contained.md)
131. **No condition may quantify over the record** — that the work contradicts no decision, that everything traces back to one. No copy repairs it, there being no bounded material. A demand about **what changed in the tree** stays permitted. The duty is owed on the handover's `INVALIDATIONS` instead.

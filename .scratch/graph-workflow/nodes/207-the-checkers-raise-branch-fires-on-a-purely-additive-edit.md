# The checker's raise branch fires on a purely additive edit to a shipped standard

Type: implementation
Status: open

Blocked by: none

## Question

*Raised by [node 197](197-ship-what-a-file-of-the-map-admits.md)'s checker alongside its `PASS`, and pasted as it
wrote it. Two earlier checkers this session reached the same clause and worked around it without saying this.*

> About the checker contract, not this condition, and it blocks nothing. `expedition-checker/SKILL.md`, under "Where
> the work moved one of them", tells a checker to compare the standard's operative elements as sets and then: "An
> element was added, removed or altered. The operative standard has itself moved... Raise it." Read literally, that
> forces a raise on *any purely additive* edit to a shipped file that the rules file also names as a standard —
> which is precisely what this node's condition demands, so the branch would make this class of work permanently
> uncheckable. I did not take it, because the branch's own stated reason ("you have nothing unmoved left to hold the
> rest of the work against") is false here: nothing pre-existing was removed or altered, and the single added
> element governs the map's files rather than the shipped file under check. If the human wants that reading enforced
> instead, this node's PASS was reached on the other one; if not, the branch may want a clause distinguishing an
> added element that does not reach the work from one that does.

**Blockers:** none stated. Its author raised it as a question rather than minting the node, so it named none.

## Acceptance condition

**None. Its author wrote none, and the manager did not write one.** The question was handed back as a checker's
question alongside an outcome, not as a minted node, so no condition came with it. Writing one is the manager's
to refuse: whoever authors the standard the work is judged against is not the manager. The condition is owed by
whoever the human sends at it, or by the human.

## The manager's note at filing

*Not a change to anything above.*

**This is the third arrival of the same clause this session and the first plain statement that its literal reading
is unworkable.** The two earlier checkers each settled the branch in a preamble and moved on; this one named the
consequence — that the class of work is uncheckable under the literal reading — and disclosed which reading its
`PASS` was reached on. **The manager raised the choice at node 197's gate** — mint on the human's word, or mint
anyway on approval — and the approval came, so it is minted with the arrival count as its whole ground and no view
of the manager's on which reading is right.

**Every node whose work adds to a shipped file the rules file also names as a standard is in this class**, which
includes the shipped half of most of this effort's own remaining work.

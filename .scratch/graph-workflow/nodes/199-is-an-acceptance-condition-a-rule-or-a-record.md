**Q1. Which side is an acceptance condition on**

**ASK:** When a live acceptance condition is amended, is its superseded clause struck through in place inside the
condition block — the record treatment, and what all nine amendments did — or is it replaced by its new form with
the old text banked verbatim to `map-history.md`, the rule treatment?

**RECOMMENDED:** **Struck in place — the record treatment — but ratified on a ground the practice never had.** I
concede the rule-side point: a live condition binds a worker exactly as a rule does, and your words *"I don't think
there should be a never delete rule on the rules. They can change"* protect a reader of a working file from meeting
a rule that no longer binds. What breaks the tie is **time**. Every other rule-side member of the bar binds
indefinitely; a condition binds for the life of one node, days at most, and is a record for the rest of the graph's
life. `map-history.md` exists because a superseded map rule has nowhere else to live. A superseded condition clause
has a perfectly good home — its own node file, already the archive of everything else about that node, and the only
place anyone would look. So the right statement is not *"a condition is a record"* but **"a node file is its own
history file"**, which is why the banking half has nothing to add. Two supports: `graph-conventions.md` already
names the node files on the record side, and node 143 already wrote this ground down. Two costs accepted: a live
worker reads struck clauses interleaved with binding ones, and node 218's condition is now five strikes deep.

**ALTERNATIVES:**
- Full rule side per node 189's letter: replaced, banked verbatim to `map-history.md`. Honest to the "binds a live
  worker" test and to the `CONDITION-WRONG` marker; makes all nine existing amendments non-conforming, severs each
  clause from its node, and puts per-node material in the map's history file.
- Replace in place, bank in the same node file: the condition block always reads clean, the old text goes to a block
  lower down in the same node. Buys the clean-read property without the severance; costs a new section in the node
  format.
- Whole-block supersession: each amendment restates the whole condition, striking the prior block entire. Cleanest
  to read; node 218 would hold six full copies.
- Exempt conditions from never-delete entirely. Cheapest; loses the trail of what a worker was actually held to.

**Q2. Whether the answer states a general test, or only settles conditions**

**ASK:** Node 198's worker hit this same cut on ordinary passages of `map.md`, not on a condition, and flag `225.2`
turns on it too. Should this node's answer state a **general test** any agent can apply to any passage — how to tell
whether the text before it states a rule or records a fact — or stay narrow and settle only the acceptance-condition
case?

**RECOMMENDED:** **State the general test.** Three agents re-derived this cut independently in one day, on three
different passages, and two raised it rather than acting. That is the exact shape node 189 was minted to close, and
node 189 closed it only for the examples it happened to enumerate. A test costs one sentence and retires the class.
My proposed test, offered for you to accept or replace: **text is rule-stating if an agent could act differently
because of it today; it is record-stating if it only tells you what was already decided or done.** Node 198's worker
reached the same place unaided — *"a pointer saying what a file contains records a fact rather than states a binding
rule."*

**ALTERNATIVES:**
- Stay narrow to conditions; leave the general case to whatever node picks up `198.1`.
- Mint a separate node for the general test, keeping this node's scope as filed.

**Q4. Whether an amendment gets one stated form**

**ASK:** Whichever side Q1 lands on, should the answer fix **one form** an amendment takes, so every future one
looks the same?

**RECOMMENDED:** **Yes, and this is the part with a correctness cost attached.** The nine amendments took five
different shapes: inline `~~strike~~` with the replacement beside it (190, 218, 226, 35); the old clause left
entirely unstruck with new prose appended beneath (184); the clause untouched with the amendment in a following
paragraph plus a separate annotation section (160); a `[!IMPORTANT]` block prepended to the condition (143); and the
section heading marked with the real text in a separate section (140, 200). **Node 200's shape is unsafe**: its
`## Acceptance condition` section is entirely unmarked, and the amending section sits elsewhere with nothing
pointing to it from the condition — so a checker handed that node cold reads superseded text as live. That is
precisely the failure node 143's checker caught and forced a fix for. My recommendation is the inline form — strike
the clause where it stands, replacement immediately beside it, carrying the reason and your words — because it is
what six of the nine already do, it keeps the condition readable top to bottom, and it makes the unsafe shape
impossible.

**ALTERNATIVES:**
- Fix the side at Q1 and leave the form to the manager's judgement each time.
- Require a pointer from the `## Acceptance condition` heading to any amendment held elsewhere, and otherwise leave
  all five shapes permitted — the minimum that closes the unsafe case.
- Require the whole condition be restated on every amendment, which makes form and side one decision.

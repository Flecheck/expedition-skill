# Rules added to one effort's map, and what makes them legitimate

Type: grilling
Status: resolved

## Question

**The human asked for this node.** Their words, `verbatim`, given alongside their answer to [How a condition's scope
is amended](82-amending-a-condition-whose-scope-was-too-narrow.md): *"I also think we should add a grilling node to
look into custom rules, rules added to the map only for one effort (example: retrospective)"*.

**The example is real and is running now.** [map.md](../map.md) carries, as a standing preference, *"Every worker
returns a retrospective as a sixth handover part, on this effort only"* — the human's own standing instruction,
**effort-scoped and never shipped**, so it is carried in every spawn and changes no worker contract. It is the
clearest case of the thing this node is about: a rule that binds every worker on one effort, lives only in that
effort's map, and has no counterpart in any shipped file.

**It is not the only one.** This map already carries several rules of the same kind, and they were added one at a
time without anything saying what makes such an addition legitimate or how a worker is meant to tell one from a rule
of the workflow. Among them: that the manager never idles and proposes the next work as each node finishes; that
approving a node's end settles that node's flags; that token-use improvement outranks the rest of the frontier; the
effort's **ground rules** block, which is copied verbatim into every checker spawn; and the **four standing rules for
writing anything in this effort**. Each is cited on the node that produced it, and none is marked as effort-scoped
in a way a reader could act on.

### What makes this a question rather than housekeeping

- **A worker cannot tell the two apart.** Every worker reads the whole map cold. Nothing in it distinguishes *this
  binds you because the workflow says so* from *this binds you because this effort's human said so*, and the
  manager's own contract already warns against presenting the second as the first: *"Record it as theirs, in their
  words, and never present it as a rule of the workflow: the next effort starts without it."* That duty is stated
  for the manager and nothing enforces it in the file.
- **One of them travels to a blind checker.** The ground rules block is copied as text into every checker spawn, and
  [The checker's spawn carries the effort's ground rules](42-checker-spawn-carries-ground-rules.md) already fixed a
  test for what may go: *a standing constraint true of any node's work, rather than an account of what happened.*
  Whether that test governs all effort-scoped rules or only the ones in that block is unstated.
- **Nothing says how one is retired, or whether it survives the effort.** The retrospective is marked *never
  shipped*; the four standing rules of writing are not marked either way, and they read like candidates for the
  shipped set.
- **The map is the only durable home for them**, per [What the manager works on next, and how the human redirects
  it](16-human-steering.md), and the map is also what every worker pays for on every node. So the cost of a custom
  rule is charged to every node of the effort, which bears on how many an effort should carry.

### Adjacent, and not this node's to settle

- [Pruning a long-running map](70-pruning-a-long-running-map.md) is about the map's size rather than about what may
  be added to it.
- [Whether charting an effort establishes and records that it is expected to end](91-charting-records-whether-an-effort-ends.md)
  found that the manager's contract has no section on starting an effort at all — which is where a custom rule would
  most naturally be declared, if declaring one is a step.

## Interview

### Attempt 1 — where a standing rule lands, and who decides whether it ships

**Q1, from the worker.** *"When a standing rule of this kind is added, must it land in this effort's map first and
stay there until a node decides to ship it — or may the manager carry it straight into a shipped file whenever it
judges the rule to be about the workflow rather than about this effort?"* Its recommendation, in its words: *"Map
first, always. Shipping is a separate decision on its own node, never the manager's call in the moment."* Its three
alternatives were that the manager judges and ships directly, that rules stay in the map forever with shipping left
to a different effort, and that **the human marks each rule's scope when stating it** — which the worker set aside on
the ground that it *"puts a question in front of you every time you give an instruction, which is the cost this
workflow exists to avoid."*

**A1, from the human**, `verbatim`: *"Write it in the map first. In efforts in other projects it will be only in the
map as there will be no modifying the skills. For this effort, I can say to add a rule to this effort or to create a
node depending on if I want it to be for the effort only or to change the skill itself."*

**The option taken, in part**, quoted from the worker, which wrote it: *"Map first, always."* Clause 1 of the
recommendation is taken as offered.

**`DIVERGENCE` on the second half.** The worker recommended that carrying a rule into a shipped file *"is its own
node, never the manager's call in the moment"*, and **set aside the alternative in which the human marks the scope**.
The human's answer takes that set-aside alternative for this effort: *"I can say to add a rule to this effort or to
create a node depending on if I want it to be for the effort only or to change the skill itself."* So the party that
decides whether a rule ships is **the human when they state it**, rather than a node decided afterwards. The worker's
stated cost for that route — that it puts a question in front of them every time — is answered by the human electing
to volunteer it rather than be asked.

**A third thing in the answer that neither the question nor the alternatives raised**, and it is about efforts other
than this one: *"In efforts in other projects it will be only in the map as there will be no modifying the skills."*
That makes *map-only* the ordinary case and shipping the exception peculiar to an effort whose subject is the
workflow itself.

## Answer

*Written by the node's worker and pasted as it wrote it.*

**A standing rule the human gives goes into the effort's map when they state it, and on most efforts that is the only
place it will ever live. It reaches a shipped skill file only where the human says so, and never on the manager's
judgement.**

The human's words, `verbatim`: *"Write it in the map first. In efforts in other projects it will be only in the map
as there will be no modifying the skills. For this effort, I can say to add a rule to this effort or to create a node
depending on if I want it to be for the effort only or to change the skill itself."*

### 1. Map first, and the map is what makes a rule bind

A standing rule lands in `map.md`'s `## Notes` at the moment it is stated. That is what makes it bind on this effort,
and it binds nobody until it is there — a node that intends to ship it later changes nothing today.

This **widens** [What the manager works on next, and how the human redirects it](16-human-steering.md) rather than
contradicting it. That node gave the map as the only durable home for a standing *scope or emphasis* — steering,
about what gets worked. The same home now takes a standing rule of any kind, including rules of conduct that steer
nothing: the retrospective duty, the shape of a report, how a node's flags are settled. Its argument carries over
unchanged and was never specific to steering — a rule held only in the manager's context dies with the thread, and
the map is read once per node by every worker.

### 2. Map-only is the ordinary case, and shipping is peculiar to this effort

On an effort in another project the workflow's skill files are not modified at all, so a rule the human gives lives
in the map and nowhere else, and the next effort starts without it. **That is the normal shape of a custom rule.**
This effort is the exception, and it is the exception for one reason: its subject is the workflow itself, so a rule
about how the manager behaves is simultaneously a rule of this effort and a candidate for the product.

This node's own `## Question` was framed the other way round — as though shipping were the default and
effort-scoping the thing needing justification. It is not, and the framing is superseded here.

### 3. The human declares the scope, when they state the rule

Two acts, theirs, in their own words: *"add a rule to this effort"*, or *"create a node"* to change the skill itself.
The party that decides whether a rule ships is the human, at the moment they give it.

**Where they say neither, the rule is the effort's alone.** Map-only is the base state, so shipping is an election
and silence is not one. The manager does not infer that a rule about the workflow was meant for the workflow; the
shipped contract's own duty — *"Record it as theirs, in their words, and never present it as a rule of the workflow:
the next effort starts without it"* — already forbids exactly that inference, and this node supplies the missing half
of it: what to do instead, which is wait to be told. Flagged, the human having named the two acts without saying what
silence means.

**This is the human's answer and not this node's recommendation.** The recommendation put to them was that shipping
be a decision the graph makes on its own node, and it explicitly *set aside* the option where the human marks each
rule's scope, on the ground that it would put a question in front of them every time they gave an instruction. They
took the set-aside option. The cost objection is answered by their electing to **volunteer** the scope rather than be
asked for it — which is not what the objection predicted, and is theirs to offer rather than something the argument
foresaw. `DIVERGENCE` is recorded on the node's `## Interview`.

The node form survives inside the human's answer rather than as a rival to it: *"create a node"* is one of the two
acts they named, so where a rule does ship, a node is still the vehicle and the manager's pick report still surfaces
it.

### 4. A worker is owed no scope marking, and this dissolves the node's first premise

The node premised that a worker cannot tell *this binds you because the workflow says so* from *this binds you
because this effort's human said so*, and treated that as the defect. **It is not one.** Every line of the map binds
every worker on the effort whatever its origin, so the two cases are indistinguishable precisely because nothing
turns on distinguishing them. The party that needs the distinction is the human and the manager, and it matters at
exactly one moment: when something is being written into a shipped file. On an effort where the skills are never
touched, that moment never comes.

So no marking is owed for a worker's sake, and the map gains no per-rule scope field. Flagged.

### 5. The ground rules block is a derived view, not a second home

The map holds one category of effort rule, in `## Notes`. The **ground rules** block is a subset of it, selected for
a different purpose: [The checker's spawn carries the effort's ground rules](42-checker-spawn-carries-ground-rules.md)
fixed a test — *a standing constraint true of any node's work, rather than an account of what happened* — for what
may be shown to a blind checker. The map says so of its own block, in the sentence beginning *"Every rule above is
drawn from a standing preference"*.

That answers the node's second bullet: node 42's test governs **what may travel to the checker**, and is not a test
for what the map may carry. A custom rule needs no ground-rules-block property to be legitimate. It may fail node
42's test and remain a perfectly good rule of the effort — the retrospective duty is one, being about a worker's
handover rather than about the shape of any node's work.

### 6. Retirement and survival

**A map rule dies with the effort.** That is what *the next effort starts without it* means, and it is the whole of
the survival question: a rule survives only by having been shipped, which happens only where the human said so.
Nothing has to retire it.

**Retirement mid-effort is the standing never-delete rule and needs no mechanism of its own** — the rule is marked as
superseded in place and the replacement is written around it, as with any map item.

This closes the node's third bullet. The four standing rules of writing, which that bullet says *"read like
candidates for the shipped set"*, are under this answer the effort's own unless and until the human says otherwise:
they were fixed by [What the token findings change in the workflow and its skills](53-what-token-findings-change.md)
rather than given by the human, and a node-fixed rule falls under the same default as a human-given one. Flagged.

### 7. Two rules of the human's currently owe a map entry, and writing them is bookkeeping

Under section 1 both bind only once they are in the map, and neither is:

- *"proactively start new nodes when one has finished"* — the map's existing entry states the earlier, weaker form
  (the paragraph beginning *"The manager never idles"*); the strengthening is not there. [Node
  100](100-the-manager-starts-the-next-node-rather-than-proposing-it.md) is shipping it.
- *"always end with a short phrase that says what is expected of the user"* — absent from the map entirely. [Node
  96](96-every-manager-report-ends-with-what-is-expected.md) is shipping it.

**Writing both is the manager's ordinary bookkeeping and not this node's work**, said here because nobody else will
say it. The map is manager-maintained, this node decides the rule rather than applying it, and a worker does not
write a graph file that is not its own node's work. The first was already owed under node 16 as steering; the second
is owed under this node, being conduct rather than steering. Both are owed independently of whether 96 and 100 land,
and the map entries stay after they do.

### 8. The one worked instance already in the corpus

The map's retrospective entry is the only rule marked **"effort-scoped and never shipped"**, and it is the human's
own example. Under this answer that marking is not a special annotation on one rule — it is the default state of
every rule in the map, and the entry is redundant rather than exemplary.

A second instance, in the opposite direction, is the shipped manager contract's flag-settlement paragraph. It ships
the rule while marking it *"one effort's standing instruction from its human rather than a rule of the workflow"* and
giving the next manager a default: *"Where an effort's human has not said it, ask."* That is the shape a rule takes
**after** the human elects to ship it — the rule travels, its source travels with it, and the next effort is told
what to do having not said it. Nothing required that shape; it is worth keeping as the form.

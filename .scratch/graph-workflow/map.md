# Map: a graph workflow that ends in finished code

**Every worker reads this whole file, cold, once per node, so it holds only what every worker can act on.** Where a line below has an account behind it — how it came to say what it says — that account is in [map-history.md](map-history.md), moved there verbatim by [Restructure `map.md` to what every worker needs](nodes/59-restructure-the-map.md): read that file when a line here has more history than it states, and this one to work a node. Whether the split falls in the right place is settled by measurement rather than argument — a worker reporting what this file did not tell it is [A worker reports what the map did not tell it](nodes/60-worker-reports-map-shortfall.md).

**What only the manager acts on is in [map-manager-only.md](map-manager-only.md)**, a part of this map that no worker reads: the review route, the dogfood target, the label vocabulary, the fog, and what is out of scope — moved there by [Move the manager's material out of the map, and give each item a soft size target](nodes/139-move-the-managers-material-out-of-the-map.md).

## Destination

A working, dogfooded workflow living in this repo: skill files, plus any harness they need, that take a loose idea all the way to a state where the code is finished and correct — driven by a manager thread that owns a graph of issues and spawns one subagent per issue, where implementation issues are first-class and revisable.

Reached when the workflow has been run end to end on at least one real effort.

**This effort is expected to end.** Written in under [Whether charting an effort establishes and records that it is
expected to end](nodes/91-charting-records-whether-an-effort-ends.md), whose answer makes this one line the place a
manager reads an effort's own expectation instead of inferring it. Under [Done-ness and
termination](nodes/10-done-ness.md)'s taxonomy this is a bounded delivery effort, so its frontier emptying is the
**milestone** that triggers the whole-graph sweep and the report preceding a close, rather than a surprise. Changed
later like any other map item, by the `Change the map` procedure.

## Notes

**This map carries execution.** Wayfinder is normally plan-don't-do; this effort overrides that, as the skill's Notes block permits. Implementation is in scope, and the destination is working files rather than a spec. Reason: the deliverable is mostly prose instructions, so a spec precise enough to build from would be the same document written twice — and designing an implementation-first workflow via spec-then-build would contradict the thing being designed.

**Domain.** Agent workflow design. The artifact is skill files (markdown), possibly with bundled `scripts/`. Direct ancestor is Matt Pocock's `/wayfinder`, which this supersedes for efforts it is run on; the orchestration shape is borrowed from [firstmate](https://github.com/kunchenguid/firstmate) (one liaison, a crew behind it).

**Skills every session should consult:** `/grilling` and `/domain-modeling` by default, `/naming` for terminology, `/coding-principles` before writing code, `/prototype` for prototype nodes. **Plus one file, not a skill:** [`CONTEXT.md`](../../CONTEXT.md) at the repo root is the glossary, and reading it is a precondition for writing anything — its `_Avoid_` lines are what stop a settled term from drifting back.

**Standing preferences for this effort:**

- Prefer short, simple prose and code that can be changed later over machinery built for predicted needs. Reserve heavy design for the hard-to-reverse core — the graph structure and revision semantics.
- **The human is the scarce resource.** Parallelism exists to saturate the human, not the machine. **This is right about what to optimise and wrong about what fails first**, per [Friction from running this map by hand](nodes/24-self-hosted-friction.md): the human never broke, and what did was the manager's own context — budgeted at 100k per node by the inherited sizing rule and measured at ~200k, compacted between nodes as standing procedure.
- **Most of the context lives in the workers, not in the manager.** The human's stated intent, verbatim: *"Ideally in the final workflow, most of the context is in the workers and not in the manager."* It governs decisions no single node owns — what a spawn carries, what a handover returns, whether the manager renders or points, and whether the manager grills a node itself when it could delegate. A manager that ends a node holding everything the node held has failed at its job even if the node resolved.
- The human only ever talks to the manager thread. A subagent never answers its own HITL question.
- **The human is asked one question at a time, and the number of nodes that may need them is a target the manager tops up to.** Their instruction, `verbatim`, after the manager stacked two questions: *"You forgot that it should be only one question at once."* And, setting the count and the rule that maintains it, `verbatim`: *"For 100, I would say by default 2 grilling nodes at once, and the rule is that when a node finishes, you start a new one (or new ones) to get back to the current amount (2 by default by the user can ask for more)"*. So: **exactly one question is in front of the human**, everything else queues and the manager serves the queue one at a time; and **the target for concurrently running nodes that need the human is two for this effort**, settable by them, with the manager starting whatever it takes to return to that target the moment a node finishes. **A live question does not block a start** — the started node's question queues like any other. The count is a per-effort setting exactly as the code slot is. Shaped by [Concurrency model](nodes/04-concurrency-model.md) and set at [The manager starts the next node rather than proposing it](nodes/100-the-manager-starts-the-next-node-rather-than-proposing-it.md). The earlier wording is in [map-history.md](map-history.md).
- **The node files are written for agents. The human works from the manager's chat and from code review.** Their words, `verbatim`, at [Carry the recorded deltas into the shipped skill files](nodes/26-carry-deltas-into-shipped-files.md)'s gate: *"I expect the nodes to be mostly targeted to agents, as I will mostly work from what the manager says (questions from subagents) and with code review."* **Narrowed by document class** at [What the token findings change in the workflow and its skills](nodes/53-what-token-findings-change.md). Over **node files** it stands exactly as written: that reader is the next agent, claiming that node and needing it whole, so completeness for an agent beats brevity for a human. Over the **shipped worker contracts** it stands on a different ground — they are mostly format-bearing instruction text, which compresses badly — so what may be compressed there is the prose explaining why, and never the named shapes. Over **`map.md`** it does not reach: this file's reader is not the next agent in the singular but every worker on every node, each needing a different fraction. And **the human's two interfaces are the manager's chat payload and the diff**, which is why both must stand alone.

**Landing policy**, which binds this map too, since this map carries execution. An implementation node's worker works in a **git worktree** the manager creates for that node with `git worktree add` off the current `HEAD`, on a branch whose name carries the node's id, placed at `.worktrees/NN-<name>/` **inside** the repository and ignored there. **The human's instruction**, `verbatim`, after a worktree outside the repository made a gate's diff invisible to them: *"For the worktree, I think it might be needed as otherwise it is too anoying for the review"*. It requires an ignore rule, which is exactly what flag `68.2` refused to assume for a repository the workflow does not own — so this is the effort's own practice and **not** a change to what the workflow ships; the flag stands open. The changes stay **uncommitted** through the checker and through the human's gate. On approval the manager makes one path-limited commit of that node's paths, rebases the branch onto the branch the manager thread is on, re-runs the bar's commands on the rebased result, merges with `git merge --ff-only`, then removes the worktree and deletes the branch. **A rebase conflict is resolved by nobody in the moment**: the manager runs `git rebase --abort` and the node takes a correction round with the worker respawned. A post-rebase bar failure likewise takes a correction round, and the work does not land. On reject the worktree is removed and its branch deleted; where the human asks for the work to be kept, the manager commits it onto that branch before removing the directory. **Nothing is ever pushed.** **The gate payload names the worktree's path and the command that shows its diff**, because an implementation node's work is uncommitted in a checkout outside the repository and `git diff` where the human is standing does not show it — their words on being handed a gate without it: *"what are the changes ? I don't see them in git ?"*. One of the human's two interfaces is the diff, so a gate that describes one and points at nothing has not been presented. The graph's own files are *not* committed per node; they are committed periodically by the human, which is safe only because node files are append-only. Fixed by [Git and code-landing policy](nodes/11-git-and-code-landing.md) and reshaped by [Run an implementation node's work in a worktree](nodes/68-implementation-in-a-worktree.md).

**How many implementation workers run at once is a setting of the effort, and for this effort it is one.** A code slot is therefore a count rather than a property, and raising the count changes a number and no part of the lifecycle above. **A slot's occupancy is discovered by counting the live worktrees** — one per claimed implementation node — rather than by inspecting the working tree for uncommitted changes, so the human's own edits no longer read as an occupied slot. Set at [Run an implementation node's work in a worktree](nodes/68-implementation-in-a-worktree.md).

**What that supersedes**: this map used to say *"No branch is ever created or switched, nothing is ever pushed, and history is never rewritten"*, and two of those three clauses no longer hold — the workflow branches per node, and a rebase rewrites history. *Nothing is ever pushed* is the one that stands untouched. The sentence in full is in [map-history.md](map-history.md).

**The workflow will also be run on repositories this machine has never seen.** Beyond Lang, the human intends to use it on work projects elsewhere — and those are the efforts that will actually *terminate*, since Lang's will not. So nothing in the design may assume this repo, this machine, or a toolchain: prefer properties that are **discovered** over commands that are declared, and treat "works on an unknown stack" as a constraint now rather than a port later. Recorded by [Done-ness and termination](nodes/10-done-ness.md).

**Claude tokens are scarce, and a worker will eventually not be a Claude subagent.** The human's constraint at work: *"I have a limited amount of claude credits but unlimited use of gemma 4 (and probably other soon)"*, so an expedition should be able to send cheap bounded work to a cheap model and keep Claude for the hard nodes. Two axes hide in that and only one is cheap: a worker's **model** is already choosable per spawn, while swapping the **harness** cannot be done from inside one manager session at all — it needs several processes and something between them, which is the firstmate shape in the fog. **The sequencing is the human's: finish the Claude-subagent version as v1, then redraw for a heterogeneous one** — a fresh effort under this map's own rule rather than a resumption, which is what keeps v1 small. What v1 owes v2 is only insurance that costs nothing today: a worker contract that stands alone as a file, and a **measured** spend per node type from the dogfood so v2's routing is designed from data. Deliberately absent: a per-node model or capability field, the node's kind already predicting what it needs.

**Ground rules for this effort.**

1. Nothing in the shipped files may assume this repo, this machine, or a toolchain. Prefer properties that are discovered over commands that are declared.
2. Each shipped worker contract stands alone as a file, rather than depending on any skill being invocable.
3. The human talks only to the manager. No agent the workflow spawns addresses the human directly, and nothing in the files may tell one to.
4. Prefer short, simple prose that can be changed later over machinery built for predicted needs. Reserve heavy design for the hard-to-reverse core.
5. Prose deliverables are held against the `/writing-for-agents` standard, which is specific to this repo, is never shipped, and is located by name in the `mattpocock-skills` plugin rather than by path.

Every rule above is drawn from a standing preference, and every one passes the test [The checker's spawn carries the effort's ground rules](nodes/42-checker-spawn-carries-ground-rules.md) shipped for what may travel to a blind checker: **a standing constraint true of any node's work, rather than an account of what happened.** That test is what keeps the rest of this file out of the block, and the block is appended to like any other part of this map.

**Four standing rules for writing anything in this effort**, fixed by [What the token findings change in the workflow and its skills](nodes/53-what-token-findings-change.md) and held against every prose deliverable. They are rules of writing, where the ground rules above are rules of scope.

1. **Compress the prose that explains why; never compress the shapes.**
2. **An item states its current form and cites the nodes that shaped it; it does not restate what they hold.**
3. **A long answer is navigable by heading**, so a reader following a link for one fact reads one section.
4. **Cite a file by heading or by a quoted phrase, never by line number.** Append-in-place shifts every line below the append, so a line number decays without anything reporting it.

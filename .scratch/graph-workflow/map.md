# Map: a graph workflow that ends in finished code

**Every worker reads this whole file, cold, once per node, so it holds only what a worker can act on.** Where a line below has an account behind it — how it came to say what it says — that account is in [map-history.md](map-history.md), moved there verbatim by [Restructure `map.md` to what every worker needs](nodes/59-restructure-the-map.md): read that file when a line here has more history than it states, and this one to work a node. Whether the split falls in the right place is settled by measurement rather than argument — a worker reporting what this file did not tell it is [A worker reports what the map did not tell it](nodes/60-worker-reports-map-shortfall.md).

## Destination

A working, dogfooded workflow living in this repo: skill files, plus any harness they need, that take a loose idea all the way to a state where the code is finished and correct — driven by a manager thread that owns a graph of issues and spawns one subagent per issue, where implementation issues are first-class and revisable.

Reached when the workflow has been run end to end on at least one real effort.

**This effort is expected to end.** Written in under [Whether charting an effort establishes and records that it is
expected to end](nodes/91-charting-records-whether-an-effort-ends.md), whose answer makes this one line the place a
manager reads an effort's own expectation instead of inferring it. Under [Done-ness and
termination](nodes/10-done-ness.md)'s taxonomy this is a bounded delivery effort, so its frontier emptying is the
**milestone** that triggers the whole-graph sweep and the report preceding a close, rather than a surprise. Changed
later like any other map item, by the `Change the map` procedure.

## Notes

**This map carries execution.** Wayfinder is normally plan-don't-do; this effort overrides that, as the skill's Notes block permits. Implementation is in scope, and the destination is working files rather than a spec. Reason: the deliverable is mostly prose instructions, so a spec precise enough to build from would be the same document written twice — and designing an implementation-first workflow via spec-then-build would contradict the thing being designed.

**Domain.** Agent workflow design. The artifact is skill files (markdown), possibly with bundled `scripts/`. Direct ancestor is Matt Pocock's `/wayfinder`, which this supersedes for efforts it is run on; the orchestration shape is borrowed from [firstmate](https://github.com/kunchenguid/firstmate) (one liaison, a crew behind it).

**Skills every session should consult:** `/grilling` and `/domain-modeling` by default, `/naming` for terminology, `/coding-principles` before writing code, `/prototype` for prototype nodes. **Plus one file, not a skill:** [`CONTEXT.md`](../../CONTEXT.md) at the repo root is the glossary, and reading it is a precondition for writing anything — its `_Avoid_` lines are what stop a settled term from drifting back.

**Standing preferences for this effort:**

- Prefer short, simple prose and code that can be changed later over machinery built for predicted needs. Reserve heavy design for the hard-to-reverse core — the graph structure and revision semantics.
- **The human is the scarce resource.** Parallelism exists to saturate the human, not the machine. **This is right about what to optimise and wrong about what fails first**, per [Friction from running this map by hand](nodes/24-self-hosted-friction.md): the human never broke, and what did was the manager's own context — budgeted at 100k per node by the inherited sizing rule and measured at ~200k, compacted between nodes as standing procedure.
- **Most of the context lives in the workers, not in the manager.** The human's stated intent, verbatim: *"Ideally in the final workflow, most of the context is in the workers and not in the manager."* It governs decisions no single node owns — what a spawn carries, what a handover returns, whether the manager renders or points, and whether the manager grills a node itself when it could delegate. A manager that ends a node holding everything the node held has failed at its job even if the node resolved.
- The human only ever talks to the manager thread. A subagent never answers its own HITL question.
- **The human is asked one question at a time, and the number of nodes that may need them is a target the manager tops up to.** Their instruction, `verbatim`, after the manager stacked two questions: *"You forgot that it should be only one question at once."* And, setting the count and the rule that maintains it, `verbatim`: *"For 100, I would say by default 2 grilling nodes at once, and the rule is that when a node finishes, you start a new one (or new ones) to get back to the current amount (2 by default by the user can ask for more)"*. So: **exactly one question is in front of the human**, everything else queues and the manager serves the queue one at a time; and **the target for concurrently running nodes that need the human is two for this effort**, settable by them, with the manager starting whatever it takes to return to that target the moment a node finishes. **A live question does not block a start** — the started node's question queues like any other. The count is a per-effort setting exactly as the code slot is. Shaped by [Concurrency model](nodes/04-concurrency-model.md) and set at [The manager starts the next node rather than proposing it](nodes/100-the-manager-starts-the-next-node-rather-than-proposing-it.md). The earlier wording is in [map-history.md](map-history.md).
- **The node files are written for agents. The human works from the manager's chat and from code review.** Their words, `verbatim`, at [Carry the recorded deltas into the shipped skill files](nodes/26-carry-deltas-into-shipped-files.md)'s gate: *"I expect the nodes to be mostly targeted to agents, as I will mostly work from what the manager says (questions from subagents) and with code review."* **Narrowed by document class** at [What the token findings change in the workflow and its skills](nodes/53-what-token-findings-change.md). Over **node files** it stands exactly as written: that reader is the next agent, claiming that node and needing it whole, so completeness for an agent beats brevity for a human. Over the **shipped worker contracts** it stands on a different ground — they are mostly format-bearing instruction text, which compresses badly — so what may be compressed there is the prose explaining why, and never the named shapes. Over **`map.md`** it does not reach: this file's reader is not the next agent in the singular but every worker on every node, each needing a different fraction. And **the human's two interfaces are the manager's chat payload and the diff**, which is why both must stand alone.
- **An in-place update never deletes.** When any file in the graph is edited — a node or this map — superseded text is marked as superseded and left where it is, and new text is added around it. Information leaves a file only when it is clearly wrong or the human asks for it gone. Quiet deletion is most damaging and least visible in the map itself.
- Tracker is local markdown (no issue tracker configured): this map and its nodes are the files in this directory.
- **The manager never idles, and *starts* the next work itself the moment a node finishes.** Two standing instructions of the human's, the second strengthening the first. `verbatim`: *"You can start new tasks. You should automatically propose to start a new task when a task finish"*, and then *"Also the manager should proactively start new nodes when one has finished"*. **Proposing is not enough**: the manager picks, spawns the worker, and reports the pick as work already under way. That report awaits no answer and takes no place in the human's queue, and their redirection of a pick is a correction after the fact rather than a permission that was waited for. What bounds how much is started is two counts, each a setting of this effort: the code-slot count for implementation nodes, and the target for concurrently running nodes that need the human, in the bullet below. Filed here under the rule [What the manager works on next, and how the human redirects it](nodes/16-human-steering.md) fixed for standing instructions, and **shipped** into the manager's contract by [The manager starts the next node rather than proposing it](nodes/100-the-manager-starts-the-next-node-rather-than-proposing-it.md), landed as commit `47703bb`. Earlier wordings are in [map-history.md](map-history.md).
- **Every report the manager puts in front of the human ends with one short line naming what is expected of them.** The human's standing instruction, `verbatim`: *"Also I want to add to the manager skill to always end with a short phrase that says what is expected of the user, like what you did now. So that can look at the last line and know what I need to look into."* The position is the point: a reader scanning only the last line must be able to tell what they must act on. Being shipped by [Every manager report ends with one line saying what is expected of the human](nodes/96-every-manager-report-ends-with-what-is-expected.md), and binding this effort from now whether or not that node has landed.
- **A standing rule binds this effort only once it is written here, and reaches a shipped file only where the human says so.** Fixed by [Rules added to one effort's map, and what makes them legitimate](nodes/93-effort-scoped-custom-rules.md). Map-only is the ordinary case — on an effort in another project the skill files are not modified at all, so a rule lives here and nowhere else and the next effort starts without it. This effort is the exception because its subject is the workflow. The human declares the scope when they state the rule, in their words: *"I can say to add a rule to this effort or to create a node depending on if I want it to be for the effort only or to change the skill itself."* **Where they say neither, the rule is this effort's alone**, and the manager never carries one into a shipped file on its own judgement. No per-rule scope marking is owed here: every line of this map binds every worker whatever its origin.
- **Approving a node's end settles that node's flags.** The human's standing instruction, `verbatim`: *"Also, when I approve the end of the node, the flags should be considered ok"*. So the manager does not ask a second time. **The settling moment is the first human moment the node's close reaches** — an implementation node's **gate** where it has one, and otherwise the **pick report** that closes the node — fixed at [A node's flags arrive after the human moment that was supposed to settle them](nodes/99-flags-arrive-after-the-node-s-human-moment.md) and widened to every kind of node, `prototype` and AFK kinds included, at [Whether a research node's and an AFK precondition node's flags settle at the pick report too](nodes/102-do-afk-nodes-flags-settle-at-the-pick-report.md), and refining the practice on [Whether flags.md survives the settle-at-close practice](nodes/27-does-flags-file-survive.md). The close is the earliest moment that works: a node's flags do not exist until its worker hands them back, which is after every exchange that node had with the human. **The pick report awaits no answer**, so the settlement rides whatever the human says next, whatever that next thing is about; where they never speak again nothing settles and those flags reach the closing report, and the manager never settles a flag on its own judgement or on the passage of time. **The consequence the manager must carry:** every report that closes a node — a gate payload, or a pick report — presents every flag that node holds, in the fuller form a gate payload uses, because a report that omits one settles it silently. The superseded wording is in [map-history.md](map-history.md).
- **Every worker returns a retrospective as a sixth handover part, on this effort only.** The human's standing instruction, `verbatim`: *"Could you, for this effort only, ask subagents, when they finish the node, a retrospective of what could be improved (making the work easier, something else), where the tokens are used, what could be done to use less tokens (better access to the information they need ? so they don't have to try to find it ? useless information ? something else ?)."* **Effort-scoped and never shipped**, so it is carried in the spawn and changes no contract. **The four questions, as the spawn puts them:** what did you have to hunt for — the fact, where you found it, where you looked first; what did you read and not use; what would have made this node easier, in the spawn, the node file, or the contract; and what did you read that was stale, wrong, or contradicted something else. **The worker is asked only what it can know** — it has no tokenizer and no view of its own usage, so it never estimates what it cost and the manager supplies the numbers. **The worker hands it back as text and the manager files it** as a `## Retrospective` annotation on the node, which keeps the mandatory section order untouched. Naming the subject is not decoration: every worker contract forbids a worker to write a graph file, so a spawn that tells one to file its own retrospective is telling it to break its contract — which happened, and the worker reported the contradiction rather than obeying, at [What a finding must carry so it can be swept](nodes/71-what-a-finding-must-carry.md).
- **Token-use improvement is prioritised above the rest of the frontier.** The human's standing instruction, `verbatim`: *"We should also bump the priority for improvement to token use"*. It is a **redirection** of [What the manager works on next, and how the human redirects it](nodes/16-human-steering.md)'s default rather than an exception to it: the alternation between a design stream and a delivery stream stands, and within each stream a node that reduces the workflow's own token cost outranks one that does not. What it does **not** license: prioritising a saving over a correctness finding, or prioritising one whose size has not been measured — **a ranking by predicted saving is the *token maxing* failure in reverse.**
- **An agent is resumed wherever it can be resumed, a checker and a dead attempt included.** Two standing instructions of the human's, given together, `verbatim`: *"The checkers should be resumed, it is expensive to figure out things multiple times. For the dead attempts it should be changed to resume also"*, and then, widening it: *"Whenever it can be resumed, resume I think"*. So the manager's default is **resume**, and respawning is what it does when resuming is not available. **It reverses two things the shipped files say** — the glossary's *"a dead worker is replaced"*, and the practice of a fresh checker per run — and the human's ground is neither of the ones the manager had in mind: it is that **rediscovering the same facts costs more than the independence it buys**, which this map already evidences, two checker runs having spent their largest single cost finding the review route. **In force on this effort from now**, under [Rules added to one effort's map, and what makes them legitimate](nodes/93-effort-scoped-custom-rules.md). **What the rule was conditional on is now measured** at [Whether a dead attempt is resumed from its transcript rather than replaced](nodes/119-dead-attempt-respawned-rather-than-resumed.md), which settles the possibility, the checker's case, and what the manager reads before resuming — the operative test being that **the manager attempts the resume and the harness answers**, a failed one starting no agent and costing nothing, so possibility is never predicted. Its one hard boundary belongs here because it bites this effort directly: **resumability dies with the manager's session**, so a handover makes every dead attempt permanently unresumable. The superseded wording is in [map-history.md](map-history.md).

**Landing policy**, which binds this map too, since this map carries execution. An implementation node's worker works in a **git worktree** the manager creates for that node with `git worktree add` off the current `HEAD`, on a branch whose name carries the node's id, placed at `.worktrees/NN-<name>/` **inside** the repository and ignored there. **The human's instruction**, `verbatim`, after a worktree outside the repository made a gate's diff invisible to them: *"For the worktree, I think it might be needed as otherwise it is too anoying for the review"*. It requires an ignore rule, which is exactly what flag `68.2` refused to assume for a repository the workflow does not own — so this is the effort's own practice and **not** a change to what the workflow ships; the flag stands open. The changes stay **uncommitted** through the checker and through the human's gate. On approval the manager makes one path-limited commit of that node's paths, rebases the branch onto the branch the manager thread is on, re-runs the bar's commands on the rebased result, merges with `git merge --ff-only`, then removes the worktree and deletes the branch. **A rebase conflict is resolved by nobody in the moment**: the manager runs `git rebase --abort` and the node takes a correction round with the worker respawned. A post-rebase bar failure likewise takes a correction round, and the work does not land. On reject the worktree is removed and its branch deleted; where the human asks for the work to be kept, the manager commits it onto that branch before removing the directory. **Nothing is ever pushed.** **The gate payload names the worktree's path and the command that shows its diff**, because an implementation node's work is uncommitted in a checkout outside the repository and `git diff` where the human is standing does not show it — their words on being handed a gate without it: *"what are the changes ? I don't see them in git ?"*. One of the human's two interfaces is the diff, so a gate that describes one and points at nothing has not been presented. The graph's own files are *not* committed per node; they are committed periodically by the human, which is safe only because node files are append-only. Fixed by [Git and code-landing policy](nodes/11-git-and-code-landing.md) and reshaped by [Run an implementation node's work in a worktree](nodes/68-implementation-in-a-worktree.md).

**How many implementation workers run at once is a setting of the effort, and for this effort it is one.** A code slot is therefore a count rather than a property, and raising the count changes a number and no part of the lifecycle above. **A slot's occupancy is discovered by counting the live worktrees** — one per claimed implementation node — rather than by inspecting the working tree for uncommitted changes, so the human's own edits no longer read as an occupied slot. Set at [Run an implementation node's work in a worktree](nodes/68-implementation-in-a-worktree.md).

**What that supersedes**: this map used to say *"No branch is ever created or switched, nothing is ever pushed, and history is never rewritten"*, and two of those three clauses no longer hold — the workflow branches per node, and a rebase rewrites history. *Nothing is ever pushed* is the one that stands untouched. The sentence in full is in [map-history.md](map-history.md).

**The dogfood target is [Lang](/home/mathieu/projects/Lang)**, decided in [Dogfood target](nodes/09-dogfood-target.md): **179 distinct gap labels across 188 inventory rows in 13 families, 43 settled decisions and 48 consistency rows** — counted by [Graph file format](nodes/13-graph-file-format.md) — a compiler that is only a lexer and parser and expects to be rebuilt, and an existing tracker doc at `Lang/docs/agents/issue-tracker.md` whose conventions this graph already borrows. **The dogfood's code lands in Lang's repository and not in this one**, per [Git and code-landing policy](nodes/11-git-and-code-landing.md), so that is the repo the landing policy has to work in. When a choice is close, prefer the one that survives that repo.

**The workflow will also be run on repositories this machine has never seen.** Beyond Lang, the human intends to use it on work projects elsewhere — and those are the efforts that will actually *terminate*, since Lang's will not. So nothing in the design may assume this repo, this machine, or a toolchain: prefer properties that are **discovered** over commands that are declared, and treat "works on an unknown stack" as a constraint now rather than a port later. Recorded by [Done-ness and termination](nodes/10-done-ness.md).

**Claude tokens are scarce, and a worker will eventually not be a Claude subagent.** The human's constraint at work: *"I have a limited amount of claude credits but unlimited use of gemma 4 (and probably other soon)"*, so an expedition should be able to send cheap bounded work to a cheap model and keep Claude for the hard nodes. Two axes hide in that and only one is cheap: a worker's **model** is already choosable per spawn, while swapping the **harness** cannot be done from inside one manager session at all — it needs several processes and something between them, which is the firstmate shape in the fog below. **The sequencing is the human's: finish the Claude-subagent version as v1, then redraw for a heterogeneous one** — a fresh effort under this map's own rule rather than a resumption, which is what keeps v1 small. What v1 owes v2 is only insurance that costs nothing today: a worker contract that stands alone as a file, and a **measured** spend per node type from the dogfood so v2's routing is designed from data. Deliberately absent: a per-node model or capability field, the node's kind already predicting what it needs.

**The graph is five files**, fixed by [Graph file format](nodes/13-graph-file-format.md) and extended by [Restructure `map.md` to what every worker needs](nodes/59-restructure-the-map.md): this `map.md`, the append-only index [decisions.md](decisions.md), the append-only [flags.md](flags.md), one file per node at `nodes/NN-<name>.md`, and [map-history.md](map-history.md), which holds the append history moved out of this map and is read for the account behind a line rather than to work a node. A node's identity is its sequential `NN`, permanently; its name is free-form and carries a foreign label when the effort was adopted from somewhere else.

**Label vocabulary for this effort: none declared.** `Labels:` is an optional per-node field holding the *family* a node belongs to, and it exists so the human can scope work to one area of a large graph. A node may only use a label declared here, so that `EFF` / `effect` / `effects` cannot drift into three labels. At 20 nodes this effort has no reader for them; an adopted effort declares its own vocabulary here — Lang's would be its 13 gap families.

**The workflow is named `/expedition`, and its vocabulary is fixed**, by [Naming](nodes/14-naming.md). The metaphor stops at the map: the product and one run of it are cartographic, and every actor and mechanism underneath is described plainly — **manager**, **worker**, **checker**, **gate**, **node**. [`CONTEXT.md`](../../CONTEXT.md) holds **50 term entries and 40 `_Avoid_` lines**, measured at [What keeps the shipped files consistent when a decision changes a term](nodes/29-shipped-file-consistency.md), and the refusals are the part that does the work: `postpone`, `provenance`, `write lock`, `done`, `issue`, `ticket` and `task` are refused by name. That file is **moving** into `.claude/skills/expedition/CONTEXT.md`, with a `CONTEXT-MAP.md` at the root and the root path left resolving as a forward pointer — [Ship the glossary inside the skill directory and make it state its own completeness](nodes/56-ship-the-glossary-into-the-skill-set.md) — because a glossary the shipped files declare authoritative and which does not travel with them is a defect. **Prose written before a word changed still says the old word: that is the never-delete rule rather than drift, and the glossary is authoritative.**

**The bar's commands for this repo, discovered on first use** and recorded here so no later node re-derives them, per [Done-ness and termination](nodes/10-done-ness.md). `graph-agent` has **no build, no tests, no formatter and no CI** — no ignore file, no manifest, no task runner, nothing to invoke. So the bar here is entirely its non-command half: the project criteria (the human's global coding principles and `/naming`), this map's own standing preferences, `CONTEXT.md`'s `_Avoid_` lines, and the node's acceptance condition. Under the *"if relevant"* clause that is a **complete** bar rather than a deficient one — the same shape the dogfood target has, one step thinner. First discovered and used by [Write the graph conventions document](nodes/21-conventions-document.md).

**The review route for this repo, discovered on first use** and recorded here so no later checker re-derives it, on the same ground as the bar's commands above. Two checker runs spent their largest single cost finding this, and one of them nearly reported the prose standard absent. **The standards to hold work against:** `/coding-principles` and `/naming`; [`CONTEXT.md`](../../CONTEXT.md)'s `_Avoid_` lines; this map's standing preferences, ground rules and four standing rules; [`graph-conventions.md`](../../.claude/skills/expedition/graph-conventions.md); and `/writing-for-agents`, which is the standard that bites on prose deliverables and which `/coding-principles` barely touches. **The reviewing skill is `mattpocock-skills:code-review`, and only part of it may run here.** Its spec step searches `docs/`, `specs/` and **`.scratch/`** for a requirements document — and `.scratch/` is this effort's record, which a checker is blind to by design, so that step is left unrun and the acceptance condition is the only statement of intent. Its standards step looks for `CODING_STANDARDS.md` or `CONTRIBUTING.md`, neither of which exists here, so the sources above are supplied by hand. Where it runs an agent of its own, that agent is **given** the standards, the paths, the diff and the condition's mandated constraints, and is **denied** the node files, `decisions.md` and `flags.md` — so it is handed no less than the checker and has nothing to go looking for. **One trap, measured:** `CONTEXT.md`'s refused words are largely unusable as a grep list, about a third being ordinary English refused only for one concept — `report`, `run`, `session`, `index`, `plan`, `item`, `question`, `where` — so a scan for them returns false positives and the distinctive refusals are checked by hand instead.

**This `## Notes` section also carries two optional blocks for whatever effort is being run**, fixed by [Subagent context contract](nodes/12-subagent-context-contract.md): the effort's **ground rules**, and a **standing over sources** declared by path and glob marking which sources are authoritative, which are evidence only, and which hold statements known to be false. Absent a declaration, every source a worker is pointed at is authoritative. They live here because this file is already a pointer every worker receives. **This effort declares a ground-rules block and no source hierarchy**, its sources all being authoritative — settled at [What keeps the shipped files consistent when a decision changes a term](nodes/29-shipped-file-consistency.md). The manager copies the block below as text into every checker spawn and adds nothing of its own, and where a check needs a constraint the block does not hold, that is a **raise** under [Whether a spawn may override a shipped worker contract](nodes/28-spawn-overriding-a-contract.md)'s rule rather than the manager's judgement.

**Ground rules for this effort.**

1. Nothing in the shipped files may assume this repo, this machine, or a toolchain. Prefer properties that are discovered over commands that are declared.
2. Each shipped worker contract stands alone as a file, rather than depending on any skill being invocable.
3. The human talks only to the manager. No agent the workflow spawns addresses the human directly, and nothing in the files may tell one to.
4. Prefer short, simple prose that can be changed later over machinery built for predicted needs. Reserve heavy design for the hard-to-reverse core.
5. Prose deliverables are held against the `/writing-for-agents` standard, which is specific to this repo, is never shipped, and is located by name in the `mattpocock-skills` plugin rather than by path.

Every rule above is drawn from a standing preference, and every one passes the test [The checker's spawn carries the effort's ground rules](nodes/42-checker-spawn-carries-ground-rules.md) shipped for what may travel to a blind checker: **a standing constraint true of any node's work, rather than an account of what happened.** That test is what keeps the rest of this file out of the block, and the block is appended to like any other part of this map.

**Four standing rules for writing anything in this effort**, fixed by [What the token findings change in the workflow and its skills](nodes/53-what-token-findings-change.md) and held against every prose deliverable. They are rules of writing, where the ground rules above are rules of scope.

1. **Compress the prose that explains why; never compress the shapes.**
2. **An item states its current form and cites the nodes that shaped it; it does not restate what they hold.**
3. **A long answer is navigable by heading**, so a reader following a link for one fact reads one section.
4. **Cite a file by heading or by a quoted phrase, never by line number.** Append-in-place shifts every line below the append, so a line number decays without anything reporting it.

- **How the human sees graph progress.** Their two interfaces are settled — the manager's narration and code review — so what is left unspecified is narrower than the item started: the **frontier** and the **outstanding flags** are surfaced by nothing, and a **parked** node, a **superseded** one, and an implementation node **holding the code slot while it waits at its gate** all read as an ordinary open node. The named dependency is the six **method skills**, none of them per-repo. What would settle it: a decision on whether expedition **vendors its own discipline** rather than borrowing its ancestor's. What is unspecified is what asynchronous review looks like from the human's side. Struck text is a rounding error — 0.4% of the node corpus — so the cost is **live restatement under append-in-place** rather than supersession. What is unspecified is the remedy, which is why this is fog rather than a node built on a guess. What would settle it: a decision on whether anything re-reads an external source, and on what trigger. ## Out of scope

- **Multi-repo and remote fleets** — firstmate's secondmates, SSH-reachable homes, cross-machine dispatch. Beyond a single-repo workflow.
- **Non-Claude-Code harness support** — Codex, Grok, OpenCode. The runtime decision picked one harness deliberately; portability is a different effort. **Still out of scope, and now with an expectation attached:** the human intends to come back for a heterogeneous fleet once v1 works, driven by Claude credit scarcity rather than preference. Under this map's own rule that is a redrawn destination and therefore a fresh effort inheriting v1's contracts, not a resumption of this one. Recorded here rather than graduated — nothing in this section becomes fog.
- **External channels** — firstmate's Relay (X, Discord). The destination names one human on one channel.
- **Cost and token accounting**, dashboards, fleet telemetry. **This line contradicts two fog items above, and [How an agent workflow and its skills reduce their own token cost](nodes/52-token-cost-of-a-workflow.md) sharpened the contradiction rather than resolving it.** The Notes above require the dogfood to carry back a **measured spend per node type**, and the fog item on runtime simplicity requires the same. Meanwhile the harness already *prints* what those ask for: `/usage` attributes recent usage to **skills, subagents, plugins and individual MCP servers** as percentages, reports cache read against cache write per model, resets on `/clear`, and raises **behavior flags** *"such as long context or cache misses, flagged when one accounts for 10% or more of recent usage"*; `/context` shows what consumes space; a statusline reading `current_usage` shows creation against read live; OpenTelemetry exports per-session cache counts. That worker's own framing, reported rather than decided: **reading numbers the harness already prints is not building accounting**, and as written this line reads as forbidding the measurement the fog demands. Not resolved here, because narrowing an out-of-scope line is a scoping act and this section's own rule is that nothing in it becomes fog without the destination being redrawn. It is one line for the human, and it is [What the token findings change in the workflow and its skills](nodes/53-what-token-findings-change.md)'s if they would rather it be decided with the rest.

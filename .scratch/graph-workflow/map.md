## Destination

A working, dogfooded workflow living in this repo: skill files, plus any harness they need, that take a loose idea all the way to a state where the code is finished and correct — driven by a manager thread that owns a graph of issues and spawns one subagent per issue, where implementation issues are first-class and revisable.

Reached when the workflow has been run end to end on at least one real effort.

**This effort is expected to end.** Written in under [Whether charting an effort establishes and records that it is
expected to end](nodes/91-charting-records-whether-an-effort-ends.md), whose answer makes this one line the place a
manager reads an effort's own expectation instead of inferring it. Under [Done-ness and
termination](nodes/10-done-ness.md)'s taxonomy this is a bounded delivery effort, so its frontier emptying is the
**milestone** that triggers the whole-graph sweep and the report preceding a close, rather than a surprise. Changed
later like any other map item, by the `Change the map` procedure.

## Notes

**This map carries execution.** Wayfinder is normally plan-don't-do; this effort overrides that, as the skill's Notes block permits. Implementation is in scope, and the destination is working files rather than a spec. Reason: the deliverable is mostly prose instructions, so a spec precise enough to build from would be the same document written twice — and designing an implementation-first workflow via spec-then-build would contradict the thing being designed.

**Domain.** Agent workflow design. The artifact is skill files (markdown), possibly with bundled `scripts/`. Direct ancestor is Matt Pocock's `/wayfinder`, which this supersedes for efforts it is run on; the orchestration shape is borrowed from [firstmate](https://github.com/kunchenguid/firstmate) (one liaison, a crew behind it).

**Skills every session should consult:** `/grilling` and `/domain-modeling` by default, `/naming` for terminology, `/coding-principles` before writing code, `/prototype` for prototype nodes. **Plus one file, not a skill:** [`glossary.md`](../../.claude/skills/expedition/glossary.md) in the skill directory is the glossary, moved there by [node 56](nodes/56-ship-the-glossary-into-the-skill-set.md), and reading it is a precondition for writing anything — its `_Avoid_` lines are what stop a settled term from drifting back.

**Standing preferences for this effort:**

- Prefer short, simple prose and code that can be changed later over machinery built for predicted needs. Reserve heavy design for the hard-to-reverse core — the graph structure and revision semantics.
- **The human is the scarce resource.** Parallelism exists to saturate the human, not the machine. **This is right about what to optimise and wrong about what fails first**, per [Friction from running this map by hand](nodes/24-self-hosted-friction.md): the human never broke, and what did was the manager's own context — budgeted at 100k per node by the inherited sizing rule and measured at ~200k, compacted between nodes as standing procedure.
- **Most of the context lives in the workers, not in the manager.** The human's stated intent, verbatim: *"Ideally in the final workflow, most of the context is in the workers and not in the manager."* It governs decisions no single node owns — what a spawn carries, what a handover returns, whether the manager renders or points, and whether the manager grills a node itself when it could delegate. A manager that ends a node holding everything the node held has failed at its job even if the node resolved.
- The human only ever talks to the manager thread. A subagent never answers its own HITL question.
- **The node files are written for agents. The human works from the manager's chat and from code review.** Their words, `verbatim`, at [Carry the recorded deltas into the shipped skill files](nodes/26-carry-deltas-into-shipped-files.md)'s gate: *"I expect the nodes to be mostly targeted to agents, as I will mostly work from what the manager says (questions from subagents) and with code review."* **Narrowed by document class** at [What the token findings change in the workflow and its skills](nodes/53-what-token-findings-change.md). Over **node files** it stands exactly as written: that reader is the next agent, claiming that node and needing it whole, so completeness for an agent beats brevity for a human. Over the **shipped worker contracts** it stands on a different ground — they are mostly format-bearing instruction text, which compresses badly — so what may be compressed there is the prose explaining why, and never the named shapes. Over **`map.md`** it does not reach: this file's reader is not the next agent in the singular but every worker on every node, each needing a different fraction. And **the human's two interfaces are the manager's chat payload and the diff**, which is why both must stand alone.
- **An in-place update never deletes.** **What it governs is the effort's own record — the files whose job is to hold what this effort decided and why**: today this `map.md` and its siblings, [decisions.md](decisions.md), [flags.md](flags.md), and the node files under `nodes/`. **That list illustrates and does not bound**, the test being that job rather than any file's name, so a sibling added later is inside the rule without this line being edited. **It reaches no file the workflow ships and no product code this effort changes**, which are edited, and deleted from, like any other code. **Inside the record it reaches text whose job is to record what happened** — a node's `## Answer`, a line in `decisions.md`, an entry in `flags.md`, an `## Interview` attempt, a `## Review` round — which is marked superseded in place, left where it is and never removed, with new text added around it. **Text whose job is to state a rule that currently binds is not struck in place**: when it is superseded it is **replaced** by its current form, and its existing text is appended **verbatim** to [map-history.md](map-history.md) under the heading mirroring the section it came from, struck-through text staying struck through. That is the `Change the map` procedure this map has always used, so replacing loses nothing. The ground is the human's, `verbatim`: *"I don't think there should a be a never delete rule on the rules. They can change."* **That history file is itself never replaced**, holding superseded text only. Information leaves the record only when it is clearly wrong or the human asks for it gone, and quiet deletion is most damaging and least visible in the map itself. Both boundaries are settled at [Where the never-delete rule stops](nodes/189-where-the-never-delete-rule-stops.md); the earlier wording is in [map-history.md](map-history.md).
- **The shipped files should not depend on the `mattpocock-skills` plugin.** The human's standing direction, `verbatim`: *"I also would want the skill to not depend on mattpockock, I don't know what is the status of this. Add grilling directly on the skill and for the docs part we should make something. Inspired by "/domain-modeling" and https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f"*. It goes further than ground rule 2, which requires only that each contract **stand alone as a file rather than depend on a skill being invocable**: this asks that the dependency not exist. **What it reaches, which is more than the contracts:** the `Skills every session should consult` line above, and **ground rule 5**, which locates `/writing-for-agents` in that plugin by name and against which every prose deliverable on this effort is held. **In force on this effort from now**, under [Rules added to one effort's map, and what makes them legitimate](nodes/93-effort-scoped-custom-rules.md). **It settles neither question it lands on**: what happens to the contracts' invoke-a-skill line is [Whether the contracts' instruction to invoke a method skill is doing any work](nodes/113-whether-the-method-skill-instruction-does-any-work.md), and what the workflow ships in place of `/domain-modeling` is [The docs discipline this workflow ships instead of depending on one](nodes/130-the-docs-discipline-this-workflow-ships.md). The account is in [map-history.md](map-history.md).
- **The rules a checker holds work against are given to it, never found by it — and the implementer is held against the same ones.** The human's standing direction, `verbatim`: *"Also I don't know if I have talked about it but in the checker, it shouldn't try to find the skill/rules, they should be at the map level and sent by the manager or just read by the checker. I don't know if it is still the case but we shouldn't use matt pockock skills code review skill as it is too generic. (it is easier to change the rule when its in a file than when the checker finds stuff by itself. The rules should also be used by the implementer"*. **Their stated ground is changeability**: a rule written in a file can be edited, where a rule a checker discovers for itself cannot. **In force on this effort from now**, under [Rules added to one effort's map, and what makes them legitimate](nodes/93-effort-scoped-custom-rules.md). **Where the rules live, and what a checker and the implementer are given, is [map-implementation-rules.md](map-implementation-rules.md)**, settled at [node 138](nodes/138-where-the-rules-a-checker-is-held-to-live.md) and carried out at [node 140](nodes/140-move-the-implementers-and-checkers-material-out-of-the-map.md). What the direction reached when it was given is in [map-history.md](map-history.md).
- Tracker is local markdown (no issue tracker configured): this map and its nodes are the files in this directory.
- **A standing rule binds this effort only once it is written here, and reaches a shipped file only where the human says so.** Fixed by [Rules added to one effort's map, and what makes them legitimate](nodes/93-effort-scoped-custom-rules.md). Map-only is the ordinary case — on an effort in another project the skill files are not modified at all, so a rule lives here and nowhere else and the next effort starts without it. This effort is the exception because its subject is the workflow. The human declares the scope when they state the rule, in their words: *"I can say to add a rule to this effort or to create a node depending on if I want it to be for the effort only or to change the skill itself."* **Where they say neither, the rule is this effort's alone**, and the manager never carries one into a shipped file on its own judgement. No per-rule scope marking is owed here: every line of this map binds every worker whatever its origin.
- **Nodes are grouped by file, and a related defect goes into a node that already exists.** The human's standing instruction, `verbatim`: *"You can do the groups. To avoid the issue, maybe we can make so that if it is related, put the defect in an already existing node ?"* The groups are the manager's proposal they accepted: open nodes against the same file are merged into one node whose condition carries the clauses of the nodes it replaces, and conflicts between those clauses go to the human. *The manager's reading of the second sentence:* where a worker surfaces a defect related to an open, unclaimed node, the defect is added to that node's condition as an amendment rather than minted as a new node. Shipping that rule into the contracts is [node 327](nodes/327-a-related-defect-joins-an-open-node-instead-of-becoming-a-new-one.md). And, `verbatim`: *"I think we shouldn't be too afraid of updating a node before it is started"*. *The manager's reading:* a node that is open and unclaimed may have its condition amended, by the manager or from a worker's report, without a separate question to the human first; the amendment is recorded as one, with a flag that settles at the node's gate, and a claimed node's condition stays as written. Node 327 carries this too. The account is in [map-history.md](map-history.md).

- **A decision of the human's own may be proposed for change, on the same footing as one the workflow made.** Their standing instruction, `verbatim`: *"You can offer to change a rule I made, the rules I choose where because I though they where the best at the point they where chosen, but in the spirit of this skill, as we make stuff, we discover stuff and that can make us decide an earlier desision was wrong"*. **So *whose decision it was* is not a reason to weaken a proposal**, and discovery falsifying an earlier choice is the expected case rather than an awkward one. **What it does not license:** a worker still never changes a settled decision itself, and the proposal reaches them as a question with its ground stated. What it corrected, and where it was first applied ([node 189](nodes/189-where-the-never-delete-rule-stops.md)), is in [map-history.md](map-history.md).

- **Where an agent sees that its acceptance condition forces a contradiction, that is a raise and not a flag.** The human's standing instruction, `verbatim`, given at [node 200](nodes/200-collapse-the-rules-files-two-map-history-statements.md)'s gate: *"If both the checker and implementer knew it, I would have expeted a raise at least."* The case is an agent deciding and flagging where what it decided is that a clause of the condition cannot be honoured together with a standard the work is held against. **What it does not license:** a raise on any hard clause, or a worker stopping because a condition is inconvenient; the trigger is a contradiction the agent can name between the condition and something the work is measured against. **In force on this effort from now**, and its carriage into the shipped contracts is [node 214](nodes/214-a-condition-that-contradicts-a-standard-is-a-raise.md). The two agents' readings it corrected are in [map-history.md](map-history.md).

**The workflow will also be run on repositories this machine has never seen.** Beyond Lang, the human intends to use it on work projects elsewhere — and those are the efforts that will actually *terminate*, since Lang's will not. So nothing in the design may assume this repo, this machine, or a toolchain: prefer properties that are **discovered** over commands that are declared, and treat "works on an unknown stack" as a constraint now rather than a port later. Recorded by [Done-ness and termination](nodes/10-done-ness.md).

**Claude tokens are scarce, and a worker will eventually not be a Claude subagent.** The human's constraint at work: *"I have a limited amount of claude credits but unlimited use of gemma 4 (and probably other soon)"*, so an expedition should be able to send cheap bounded work to a cheap model and keep Claude for the hard nodes. Two axes hide in that and only one is cheap: a worker's **model** is already choosable per spawn, while swapping the **harness** cannot be done from inside one manager session at all — it needs several processes and something between them, which is the firstmate shape in the fog. **The sequencing is the human's: finish the Claude-subagent version as v1, then redraw for a heterogeneous one** — a fresh effort under this map's own rule rather than a resumption, which is what keeps v1 small. What v1 owes v2 is only insurance that costs nothing today: a worker contract that stands alone as a file, and a **measured** spend per node type from the dogfood so v2's routing is designed from data. Deliberately absent: a per-node model or capability field, the node's kind already predicting what it needs.

**Ground rules for this effort.**

1. Nothing in the shipped files may assume this repo, this machine, or a toolchain. Prefer properties that are discovered over commands that are declared.
2. Each shipped worker contract stands alone as a file, rather than depending on any skill being invocable.
3. The human talks only to the manager. No agent the workflow spawns addresses the human directly, and nothing in the files may tell one to.
4. Prefer short, simple prose that can be changed later over machinery built for predicted needs. Reserve heavy design for the hard-to-reverse core.
5. Prose deliverables are held against the `/writing-for-agents` standard, which is specific to this repo, is never shipped, and is located by name in the `mattpocock-skills` plugin rather than by path.

**This effort's standing rules for writing**, held against every prose deliverable. The first four were fixed by [node 53](nodes/53-what-token-findings-change.md), the fifth by [node 289](nodes/289-a-plain-english-and-compaction-pass-over-the-shipped-files.md) and the sixth by [node 253](nodes/253-a-shipped-file-points-at-a-sibling-rather-than-restating-it.md).

1. **Compress the prose that explains why; never compress the shapes.**
2. **An item states its current form and cites the nodes that shaped it; it does not restate what they hold.**
3. **A long answer is navigable by heading**, so a reader following a link for one fact reads one section.
4. **Cite a file by heading or by a quoted phrase, never by line number.** Append-in-place shifts every line below the append, so a line number decays without anything reporting it.
5. **Write plain English.** State a rule as what to do; use a prohibition only where the rule cannot be said as what to do, and then beside the positive. Bold a term only where it is defined. Say any idea that is not a term defined in the glossary, `.claude/skills/expedition/glossary.md`, in plain words, with no figure of speech and no coined phrase. Make statements directly rather than as slogan-shaped contrasts. Write every sentence grammatically, with one clear referent for each pronoun. Put one idea in each sentence.
6. **Point at a heading of another shipped file instead of restating what it holds, where the reader is already told to read that file.** Where the reader is not, restate what the reader needs when the file pointed at is mostly text that reader does not need, so the reader is not sent to read it. A passage that changes a rule for its own case names that rule by heading and states the change in its own words. Rename a heading that another shipped file cites only in the change that updates every citation of it, found by searching the shipped files for the heading's exact text.

Every rule above, in both lists, is **a standing constraint true of any node's work, rather than an account of what happened.** That is the test [The checker's spawn carries the effort's ground rules](nodes/42-checker-spawn-carries-ground-rules.md) shipped for what may travel to a blind checker. That test is what keeps the rest of this file out of the block, and the block is appended to like any other part of this map.

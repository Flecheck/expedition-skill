## Landing an implementation node's work

**Landing policy**, which binds this map too, since this map carries execution. An implementation node's worker works in a **git worktree** **the manager creates with plain git — see *How the worktree is made* below**, on a branch whose name carries the node's id, placed at `.scratch/graph-workflow/worktrees/<NN>-<name>` **inside** the repository and ignored there. **The human's instruction**, `verbatim`, after a worktree outside the repository made a gate's diff invisible to them: *"For the worktree, I think it might be needed as otherwise it is too anoying for the review"*. It requires an ignore rule, which is exactly what flag `68.2` refused to assume for a repository the workflow does not own — so this is the effort's own practice and **not** a change to what the workflow ships; the flag stands open. The changes stay **uncommitted** through the checker and through the human's gate. On approval the manager makes one path-limited commit of that node's paths, rebases the branch onto the branch the manager thread is on, re-runs the bar's commands on the rebased result, merges with `git merge --ff-only`, then removes the worktree and deletes the branch. The manager runs `git merge --ff-only` with the sandbox off, on the first attempt as well as on any retry. The reason is that the sandbox mounts `.claude/skills` in the main checkout read-only, so a merge run inside the sandbox can fail after writing some of the changed files. The repair for a merge that was run inside the sandbox is in the bullet *One sandbox restriction bites this lifecycle* below. Settled at [node 369](nodes/369-the-landing-merge-runs-with-the-sandbox-off-from-the-start.md). A rebase conflict is resolved, and the rebase is not aborted. Who resolves it depends on what conflicted. Where the conflict is in text held under the never-delete rule, the manager resolves it by keeping both sides. That is assembly rather than authoring, so the manager reports the resolution, and the work does not return to the checker or to the gate. Any other conflict, product code included, is resolved by the worker whose branch is being rebased. The manager resumes that worker to edit the conflicted files in place, and the manager itself runs every git command. That resolution returns to the checker and to the gate. Where the two sides contradict each other, so that keeping both would make the file assert two incompatible things, the manager runs `git rebase --abort` and the node takes a correction round. Settled at [node 115](nodes/115-two-writers-edit-the-map-at-once.md). A post-rebase bar failure likewise takes a correction round, and the work does not land. On reject the worktree is removed and its branch deleted; where the human asks for the work to be kept, the manager commits it onto that branch before removing the directory. **Nothing is ever pushed.** **The gate payload names the worktree's path** ([node 231](nodes/231-a-gate-payload-stops-carrying-a-diff-command.md), [node 336](nodes/336-carry-the-rules-on-what-reaches-the-human-the-code.md)). An implementation node's work is uncommitted, so it appears in no commit the human can read, and the path is how the work is found at all. The worktree being inside the repository, where [Run an implementation node's work in a worktree](nodes/68-implementation-in-a-worktree.md) placed it, does not make its changes visible where the human is standing. The human's words on being handed a gate without the path: *"what are the changes ? I don't see them in git ?"*. One of the human's two interfaces is the diff, so a gate that describes one and points at nothing has not been presented. The manager commits the graph's own files itself, at two moments. First, it commits them before it cuts every implementation worktree, whatever paths that node's condition names, so that the tree a worker is given equals the tree the manager is standing on. Second, when the human approves a node at its gate, the manager commits its own outstanding record edits as the first step of landing, before the rebase. This is because `git merge --ff-only` is refused where a dirty file is one the branch also changes, and because a record commit made after the rebase leaves the branch unable to fast-forward. The commit at the cut keeps the worker's base current, and the commit before the rebase is what unblocks the merge, so neither one replaces the other. The manager makes both commits on its own authority, path-limited to `.scratch/graph-workflow/`. It shows the human no diff before either commit, and reports each commit to the human afterwards. An implementation worker reads and edits the effort's record files in its own worktree, and never in the main checkout. Settled at [node 115](nodes/115-two-writers-edit-the-map-at-once.md), [node 176](nodes/176-the-managers-record-edits-collide-with-a-landing.md) and [node 266](nodes/266-a-worker-cannot-see-the-record-the-manager-has-not-committed.md). Fixed by [Git and code-landing policy](nodes/11-git-and-code-landing.md) and reshaped by [Run an implementation node's work in a worktree](nodes/68-implementation-in-a-worktree.md).

**How the worktree is made, settled at [Should the worktree route drop `EnterWorktree` for plain git, behind a
script](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md).** Stated beside the landing policy above
rather than rewritten into it, because two pointers in the repository's `.gitignore` cite this section by the quoted
phrase *How the worktree is made*, and [node
152](nodes/152-where-the-harness-worktree-instruction-lives.md) and [node
144](nodes/144-make-the-rules-file-stand-alone.md) hold conditions quoting its phrases. **The route this replaces is
banked whole in [map-history.md](map-history.md).**

- **Create.** The manager makes each implementation node's worktree with one plain git command:
  `git -C <repo root> worktree add -b worktree-<NN>-<name> .scratch/graph-workflow/worktrees/<NN>-<name>`.
  `<repo root>` is the main tree's absolute path, which is the first path `git worktree list` prints. `<NN>` is the
  node's id, so the id is in the path and in the branch. Git resolves the relative path against `<repo root>`, so
  the command creates the same worktree whatever the shell's working directory is. Run from a working directory
  below the repository root without `-C`, the command creates the worktree at a doubled path such as
  `.scratch/graph-workflow/.scratch/graph-workflow/worktrees/<NN>-<name>`. The repository's `.gitignore` does not
  match that path, so `git add .scratch/graph-workflow` stages the worktree as one embedded repository entry and
  warns `adding embedded git repository`. Settled at [node
  265](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md), with the working directory fixed at [node
  284](nodes/284-the-worktree-create-command-names-a-relative-path.md).
- **Base.** That command lands the worktree on the manager's current `HEAD` by git's own default, so **no base reset
  is performed** and **no `worktree.baseRef` setting is relied on**: it is git's own semantics rather than a
  configuration, so it holds on a machine nobody has configured. Settled at [node
  265](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md).
- **Creating the worktree, putting it on its base, and writing it need no harness tool call and no sandbox
  override**, by the manager or by the worker. **The removal is the exception, and the *Remove* bullet states it.**
  Settled at [node 265](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md) and narrowed to those
  three steps at [node
  277](nodes/277-the-removal-step-of-the-worktree-route-does-not-work-as-written.md).
- **The worker writes its worktree by absolute path.** It calls no tool to reach it, enters and leaves nothing, and
  owes no cleanup — there is no first act to get wrong and no refusal to handle. Settled at [node
  265](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md).
- **Remove, and the removal runs with the sandbox off**: `git worktree remove --force <path>`, then `git branch -D
  worktree-<NN>-<name>`. **Attempted inside the sandbox the removal can fail**, on `.git/worktrees/<name>` with
  `error: failed to delete '.git/worktrees/<name>': Device or resource busy`, and **what it leaves is not a clean
  tree**: the working directory goes, the admin directory under `.git/worktrees/` stays, the entry turns
  `prunable`, `git worktree list` keeps reporting a tree that no longer exists, and the branch will not delete —
  *"cannot delete branch … used by worktree at …"*. **The recovery, for an entry already left stale**, is `git
  worktree prune` with the sandbox off, after which `git branch -D` succeeds. **What fails is the unlink of a mount
  point**: the sandbox places two bind mounts on some worktrees — `.git/worktrees/<name>` read-write and its
  `commondir` read-only — and a mount point cannot be unlinked. **Which worktrees carry them is a fit over seven
  observations rather than a demonstrated mechanism**: every worktree removed by the session that created it
  carried neither mount and came away clean, while the one removal that failed and the only other tree found
  carrying them had each outlived the session that created it. **So the trigger is a worktree outliving the session
  that made it** — and why that is what does it is unestablished, nobody having shown how the mounts come to be
  there. **The trigger is stated so that a reader knows the rule is not paranoia, and not as a condition on when to
  obey it**: a live tree shows no mount to inspect beforehand, the manager cannot always tell which case it is in,
  the override costs one call, and the failure costs a stale entry in the very thing a code slot's occupancy is
  counted from. The two commands are [node
  265](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md)'s; the rest is settled at [node
  277](nodes/277-the-removal-step-of-the-worktree-route-does-not-work-as-written.md).
- **The commit trailer `Node: <effort>/<NN>` is the join key, and it is the manager's to write.**
- **The route's one failure mode, and the read-only command that catches it.** The route works because
  `.scratch/graph-workflow` is inside the manager's sandbox writable region, and **that has not always been so** —
  in one session the manager's own shell could not append to `flags.md` in that directory while it could write the
  node files one level below. **So the manager runs `test -w <repo root>/.scratch/graph-workflow` before creating a
  worktree**, with `<repo root>` as in the *Create* bullet. Where that check fails the worktree can be **neither
  created nor written** and there is no fallback, no tool call being able to widen the region for that path, so it
  is **raised to the human** rather than worked around. Settled at [node
  265](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md).
- **A failed rebase leaves its partial checkout behind, and every retry then meets the dirt its predecessor made.**
  Measured at node 143. `git rebase` reported only `could not
  detach HEAD`; the underlying `git checkout --detach` reports the real cause, which was local changes and untracked
  files that **the previous failed rebase had itself written**. **Cleaning and rebasing in separate calls cannot
  converge.** The repair is one pass: `reset --hard` to the branch's own commit, `clean` the record directory, then
  rebase — and read `git checkout --detach <target>` rather than the rebase's summary when it fails again.

- **A correction round resumes the worker**, and where resume is unavailable the replacement is spawned without
  isolation and pointed at the worktree's absolute path. **The worktree is the manager's and outlives every worker
  in it**, so no respawn can strand work already written there. Flagged at `150.3` as unverified.
- **One sandbox restriction bites this lifecycle.** The operative rule, measured: the sandbox is a set of
  bind mounts **recomputed for every command**, and a command succeeds only where every path it writes lies
  inside a `rw` mount and outside a `ro` one. **The manager reads its own region with**
  `grep " <repo>" /proc/mounts | awk '{split($4,a,","); print a[1]" "$2}' | sort -u` — read-only, one call.
  Whether it is told to, and when, is [node 179](nodes/179-the-manager-sees-its-own-writable-region.md); what
  triggers the overlay on one tree and not another is [node
  180](nodes/180-which-trees-get-the-read-only-skills-overlay.md).
  **The three sub-bullets below are measurements, and two of the operations they name — a reset, and an *entered*
  worktree — are steps of no route any longer**, [node
  265](nodes/265-should-the-worktree-route-drop-enterworktree-for-git.md) having removed both. They are marked here
  rather than removed; the merge step they also name is still in the landing policy above, and what bites it is
  unchanged.
  - **What it hits.** `git merge --ff-only` in the main tree, of a branch that changed a file under `.claude/skills/`
    — `unable to unlink old …`. And `git reset --hard <ref>` inside an *entered* worktree, where the range crosses
    such a file — `Could not reset index file to revision`. `HEAD` does not move in either case. The reset loses
    nothing and succeeds outside the sandbox. The merge may instead write some of the changed files before it
    fails. That leaves the main tree dirty, and a retry outside the sandbox then refuses with `Your local changes
    to the following files would be overwritten by merge`. The merge can also fail having written nothing, and then
    the retry outside the sandbox succeeds. **The manager must expect this rather than discover it**, most of the
    open frontier touching `.claude/skills/`. The landing policy above has the manager run the merge with the
    sandbox off. The repair that follows applies where a merge was run inside the sandbox despite that rule.
    The repair for a partially written merge is one pass, in this
    order. First, establish that every file the failed merge left dirty is byte-identical to the branch's version
    of it: `git show worktree-<NN>-<name>:<path> | cmp - <path>` succeeds for each one. Then, outside the sandbox,
    discard those files: `git checkout HEAD -- <path>` for a file `HEAD` holds, and delete a file `HEAD` does not
    hold. Then re-run the merge outside the sandbox. Establishing byte-identity comes first. Where any dirty
    file differs from the branch's version, the manager stops and discards nothing, because that difference is
    content the branch does not carry.
    Settled at [node 234](nodes/234-a-failed-merge-can-leave-the-tree-partially-updated.md).
  - **What it does not hit, established by experiment rather than inferred.** `git add` and `git commit` from inside
    an entered worktree both succeed. `.git/index` is writable in the main tree and in a worktree's admin directory.
    `git reset --hard` succeeds inside an entered worktree where the commit range touches no file under
    `.claude/skills/`. So the operation is irrelevant; **only the paths the operation must write matter.**
  - **What decides is whether the target path is inside the writing session's writable region**, not which
    tree the command is issued from. From a session whose region did *not* contain the worktree path, `git -C
    <harness worktree> reset --hard` failed on plain `.scratch/` files with `Read-only file system`, no
    skills file involved; from a session whose region *did* contain it, the same command succeeded across a
    `.claude/skills` file. Harness worktrees do sometimes carry their own `<wt>/.claude/skills` `ro` mount.
